# CatDoor AI — контекст проекта для Codex

## Цель

Создать полностью локальную систему автоматической дверцы для домашних кошек.

Система должна:

- получать видео с двух камер;
- определять наличие кошки возле дверцы;
- идентифицировать конкретную домашнюю кошку;
- не пропускать чужих кошек;
- использовать одновременно изображение морды и боковой вид тела;
- принимать решение по серии кадров, а не по одному изображению;
- сохранять события для разметки и последующего переобучения;
- иметь локальную веб-админку;
- в дальнейшем управлять отдельным контроллером дверцы;
- работать без облачного распознавания.

RFID, NFC, ошейники и имплантируемые метки не используются. Часть кошек старше 20 лет, поэтому идентификация должна быть только визуальной.

## Аппаратная архитектура

### Постоянно работающий компьютер

Отдельный моноблок с Windows:

- Intel Core i3-8109U;
- 2 ядра / 4 потока;
- Intel Iris Plus Graphics 655;
- 16 ГБ RAM;
- SSD 512 ГБ;
- домашняя сеть через Wi-Fi;
- камеры через отдельный проводной Ethernet-сегмент.

Моноблок выполняет:

- приём RTSP-потоков;
- кольцевую буферизацию;
- запись событий;
- локальный инференс;
- объединение результатов двух камер;
- хранение журнала;
- работу веб-интерфейса;
- связь с контроллером дверцы;
- watchdog и контроль свободного места.

Моноблок не предназначен для обучения моделей.

### Компьютер для обучения

MacBook на Apple M5.

Он используется для:

- подготовки датасета;
- обучения моделей через PyTorch/MPS;
- оценки качества;
- калибровки порогов;
- экспорта в ONNX;
- подготовки релиза модели для Windows.

Готовые ONNX-модели переносятся на моноблок и запускаются через OpenVINO или ONNX Runtime.

## Камеры

Планируются две камеры с разными ролями.

### Камера 1 — морда

Задачи:

- фронтальный или близкий к фронтальному ракурс;
- обнаружение морды;
- идентификация по глазам, носу, ушам, форме головы и рисунку шерсти;
- формирование `face_score` или `face_embedding`.

Камера должна находиться примерно на уровне головы кошки, а не высоко под потолком.

### Камера 2 — боковой вид

Задачи:

- видеть корпус целиком;
- анализировать окрас, пятна, грудь, лапы, профиль головы и хвост;
- определять направление движения;
- замечать второго кота или другое животное;
- формировать `body_score` или `body_embedding`.

### Сеть

Предпочтительная схема:

```text
Камера морды ─┐
              ├── изолированный Ethernet/PoE-коммутатор
Камера сбоку ─┘                   │
                                  │ Ethernet
                           Windows-моноблок
                                  │
                                Wi-Fi
                                  │
                           домашняя сеть
```

Камеры не должны иметь доступ в интернет.

Пример подсети:

```text
Моноблок Ethernet: 192.168.50.1/24
Камера морды:      192.168.50.11/24
Камера сбоку:      192.168.50.12/24
Шлюз камер:        не задавать
DNS камер:         не задавать
```

### Имеющаяся камера

Ivideon V Ursa Minor:

- 2 Мп;
- фиксированный объектив 4 мм;
- питание 12 В;
- Ethernet;
- RTSP/ONVIF;
- возможная роль: боковая или обзорная камера.

### Вторая камера

Планируется уличная IP-камера:

- 4 Мп;
- RTSP;
- ONVIF;
- основной и дополнительный потоки;
- IP66/IP67;
- PoE желательно, но не обязательно;
- ручная настройка выдержки и подсветки;
- подходящая минимальная дистанция фокусировки.

Конкретные модели и RTSP URL не должны быть жёстко зашиты. Все параметры задаются через конфигурацию или веб-интерфейс.

## Ограничения производительности

Intel Core i3-8109U не должен постоянно выполнять тяжёлый инференс по двум полноразмерным потокам.

Нужна двухуровневая обработка.

### Постоянный режим

- использовать субпотоки 640×360 или 704×576;
- анализировать примерно 3–8 FPS;
- лёгкая модель только обнаруживает кошку и вход в зону.

### Режим события

После обнаружения:

- брать кадры основного потока;
- выбирать лучшие по резкости и положению;
- выделять морду и тело;
- запускать идентификацию;
- принимать решение по нескольким кадрам.

Предпочтительно:

- OpenVINO на Windows;
- ONNX Runtime как резерв;
- Intel Quick Sync для декодирования, если стабильно работает.

## Архитектура моделей

Не делать одну монолитную модель, принимающую два сырых кадра.

```text
Камера морды
    ↓
детектор морды
    ↓
модель идентификации по морде
    ↓
face scores / face embedding

Камера сбоку
    ↓
детектор кошки
    ↓
модель идентификации по телу
    ↓
body scores / body embedding

результаты + качество кадров + серия кадров
    ↓
fusion logic
    ↓
known / unknown / uncertain
```

### Начальный вариант

- детектор: YOLO11n, YOLOv8n или аналогичный компактный ONNX-совместимый вариант;
- классификатор морды: MobileNetV3, EfficientNet-B0 или ResNet18;
- классификатор тела: MobileNetV3, EfficientNet-B0 или ResNet18;
- отдельные состояния `unknown` и `uncertain`;
- решение по 5–10 лучшим кадрам;
- при конфликте камер дверь не открывать.

### Объединение

Начать с прозрачной взвешенной формулы:

```text
final_score =
    face_score × face_quality × face_weight
  + body_score × body_quality × body_weight
```

Начальные веса:

```text
face_weight = 0.65
body_weight = 0.35
```

Веса должны настраиваться через админку и автоматически уменьшаться при плохом качестве соответствующего ракурса.

Следующий этап — embeddings и open-set verification.

## Главная метрика

Самая опасная ошибка:

> чужая кошка принята за домашнюю.

Приоритет:

1. False Accept Rate;
2. False Reject Rate;
3. доля `uncertain`;
4. время принятия решения;
5. общая accuracy.

При сомнении система должна не открывать дверь, а сохранить событие для проверки.

## Сбор данных

Данные собираются именно с установленных камер.

Каждый проход — отдельное событие:

```text
event_id/
├── face.mp4
├── side.mp4
├── face_best_01.jpg
├── face_best_02.jpg
├── side_best_01.jpg
├── side_best_02.jpg
├── thumbnail.jpg
└── metadata.json
```

Пример метаданных:

```json
{
  "event_id": "2026-08-01_10-14-22",
  "started_at": "2026-08-01T10:14:22",
  "confirmed_cat_id": null,
  "predicted_cat_id": null,
  "direction": "unknown",
  "review_status": "pending",
  "model_version": null
}
```

### Минимум первой итерации

На каждого кота:

- минимум 100 независимых событий;
- около 500 разнообразных кадров морды;
- около 500 кадров сбоку.

Рабочая цель:

- 150–250 независимых событий;
- 800–1500 изображений морды;
- 800–1500 изображений тела;
- разные дни, освещение, погода и сезоны.

Соседние кадры одного видео не считать независимыми примерами.

### Разделение

Разделять по событиям и датам:

- 70% train;
- 15% validation;
- 15% test.

Кадры одного события никогда не должны попадать одновременно в разные части набора.

## Запись и хранение

Не вести постоянную полноразмерную запись.

Использовать кольцевой буфер:

- 10–15 секунд до события;
- само событие;
- 10–20 секунд после.

Видео и изображения хранить в файловой системе. В SQLite хранить:

- ID события;
- время;
- пути к файлам;
- результаты моделей;
- подтверждённого кота;
- действие двери;
- версию модели;
- статус разметки;
- параметры качества;
- ошибки.

Структура:

```text
C:\CatDoor\
C:\CatDoorData\
├── events\
├── dataset\
├── models\
├── exports\
├── logs\
└── backups\
```

Политика хранения:

- обычные подтверждённые события: 14–30 дней;
- ошибки и `unknown`: до ручной проверки;
- кадры датасета: бессрочно;
- временные буферы: автоматическое удаление;
- минимум 50–80 ГБ свободного места.

## Веб-админка

Предпочтительный стек первой версии:

- Python;
- FastAPI;
- Jinja2;
- HTMX;
- SQLite;
- минимум JavaScript.

Админка должна позволять без командной строки:

- видеть статус камер;
- смотреть последние кадры;
- просматривать журнал событий;
- открывать синхронные видео;
- подтверждать конкретного кота;
- отмечать `чужой`, `не видно`, `несколько котов`;
- формировать датасет;
- экспортировать ZIP для MacBook;
- загружать новую ONNX-модель;
- тестировать модель на сохранённых событиях;
- активировать и откатывать версии;
- менять веса, пороги и параметры камер;
- видеть свободное место и ошибки;
- включать тестовый режим без управления дверью.

### Пакет модели

```text
face_model.onnx
body_model.onnx
thresholds.json
model_info.json
checksums.sha256
```

Перед активацией:

1. проверить структуру;
2. проверить контрольные суммы;
3. проверить совместимость;
4. прогнать на сохранённом тестовом наборе;
5. показать отчёт;
6. активировать только после подтверждения;
7. сохранить предыдущую версию.

## Контроллер двери

Windows не управляет силовой частью напрямую.

Использовать ESP32 или Arduino:

- USB Serial на первом этапе;
- heartbeat;
- документированный протокол;
- тайм-ауты;
- локальные концевики и датчики;
- безопасный режим при потере связи;
- ручная разблокировка.

До длительного тестирования работать только в режиме:

```text
Система открыла бы дверь
```

Создать приложение без нейросети и без реального управления дверью.

Оно должно:

1. подключаться к двум RTSP-камерам;
2. показывать их статус;
3. сохранять синхронное тестовое событие;
4. вести SQLite-базу;
5. показывать журнал через браузер;
6. позволять вручную назначить событию кота;
7. экспортировать размеченные события в ZIP;
8. запускаться на Windows как служба;
9. восстанавливаться после разрыва RTSP;
