## 2. Подготовка локального окружения

Проверь версии macOS, архитектуру, Python и Git. Нужен совместимый Python,
предпочтительно Python 3.13. Если Python или системные инструменты отсутствуют,
сначала объясни, что именно требуется установить, и запроси подтверждение перед
Homebrew, Xcode Command Line Tools или командами администратора.

Создай отдельное окружение `.venv-training` и установи зависимости проекта:

```bash
python3 -m venv .venv-training
source .venv-training/bin/activate
python -m pip install --upgrade pip
python -m pip install -e ".[training,dev]"
```

Проверь окружение:

```bash
python -m ruff check .
python -m mypy src training
python -m pytest
```

Также выведи версии Python, PyTorch и torchvision и проверь:

```python
import torch
print(torch.backends.mps.is_available())
print(torch.backends.mps.is_built())
```

Если проверка выполняется из Codex, `is_built()` возвращает `true`, а
`is_available()` — `false`, повтори короткую проверку MPS вне ограниченной
песочницы после подтверждения владельца. Не делай вывод о недоступности GPU
только по результату sandbox-процесса.

Если MPS недоступен, выясни причину. Не начинай длительное обучение на CPU без
моего подтверждения.

## 3. Поиск и проверка датасета

Датасет должен оставаться только на этом компьютере. Не копируй его в
репозиторий и не загружай в интернет. Для рабочих файлов используй отдельный
локальный каталог вне репозитория, например `~/CatDoorTraining`, и сначала
создай понятную структуру каталогов.

Найди переданный экспорт разметки только в явно доступных локальных каталогах.
Не сканируй весь домашний каталог без необходимости. Если путь нельзя
однозначно определить, спроси у меня:

- абсолютный путь к `dataset.jsonl`;
- абсолютный путь к корню изображений;
- при необходимости — где хранить checkpoints, ONNX и отчёты.

Не угадывай личности котов и не создавай фиктивные метки. Проверь, что строки
манифеста соответствуют формату из документации, файлы изображений существуют,
а записи содержат как минимум `event_id`, `view`, `label` и путь к изображению.

Запусти проверку и при необходимости назначение split по событиям, а не по
отдельным соседним кадрам:

```bash
python -m training.dataset \
  /ABSOLUTE/PATH/dataset.jsonl \
  --dataset-root /ABSOLUTE/PATH/images \
  --assign-splits /ABSOLUTE/PATH/dataset.with-splits.jsonl
```

До начала обучения отдельно отчитай:

- число событий и изображений для каждой камеры (`face` и `side`);
- распределение по меткам;
- распределение train/validation/test;
- даты съёмки и возможные дубликаты;
- отсутствующие или повреждённые файлы;
- утечки одного `event_id` между split;
- наличие как минимум двух подтверждённых классов известных котов;
- наличие независимых примеров чужих животных для оценки класса
  `__foreign__`.

Не используй test для подбора гиперпараметров или порогов. Чужих животных
сохрани для независимой приёмки. Если данных, подтверждённых меток или
независимых событий недостаточно, не запускай бессмысленное обучение:
остановись, перечисли точные проблемы и предложи минимальный план доразметки.

Если вместо готового манифеста переданы только видео или экспорт событий, сначала
проверь существующие инструменты проекта. Не изобретай новый формат. Подготовку
кадров выполняй только локально, сохраняя связь с `event_id`; соседние кадры
одного прохода нельзя разносить по разным split. Метки личности должен
подтвердить человек.

## 4. Запуск обучения

Если проверка пройдена, создай отдельные локальные каталоги результатов для
центральной камеры `face` и дополнительной камеры `side`. Запусти обучение
раздельно для каждого доступного вида:

```bash
python -m training.train_classifier \
  /ABSOLUTE/PATH/dataset.with-splits.jsonl \
  /ABSOLUTE/PATH/images \
  /ABSOLUTE/PATH/runs/face/checkpoint.pt \
  --view face
```

```bash
python -m training.train_classifier \
  /ABSOLUTE/PATH/dataset.with-splits.jsonl \
  /ABSOLUTE/PATH/images \
  /ABSOLUTE/PATH/runs/side/checkpoint.pt \
  --view side
```

Используй MPS, если скрипт и окружение его поддерживают. Не запускай две тяжёлые
тренировки одновременно, если это вызывает нехватку памяти. Сохраняй логи,
метрики и checkpoints вне Git. Во время длительного запуска периодически
сообщай текущую эпоху, loss, validation-метрики, использование MPS и примерное
оставшееся время. При NaN, деградации или систематической ошибке остановись и
диагностируй причину.

## 5. Экспорт и локальная проверка

После успешного обучения экспортируй каждую пригодную модель в ONNX командами и
аргументами, описанными в `training/README.md`. Используй фактические пути к
checkpoint и `model-info`; не выдумывай имена файлов.

Проверь ONNX локально и собери пакет через:

```bash
python -m training.model_package build ...
```

Сохраняй итоговый ZIP вне исходного каталога с ONNX и метаданными, например в
`/ABSOLUTE/PATH/packages/`. Сборщик намеренно отклоняет checkpoints и другие
посторонние файлы.

Пороги неизвестности и допуска нельзя принимать как готовые только потому, что
они указаны в примере. Подбери их на validation с приоритетом низкого FAR, а
окончательный FAR/FRR и latency оставь для независимой приёмки на Windows
Intel Core i3-8109U/OpenVINO согласно
`docs/model-training-and-acceptance.md`.
