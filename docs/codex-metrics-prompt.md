## Целевая архитектура

Три слоя поверх существующей базы событий:

```text
1. Реестр версий моделей + предсказания активных моделей по каждому событию
        ↓ (ручная разметка подтверждает или опровергает)
2. Скользящие онлайн-метрики рабочей модели (FAR / FRR / uncertain)
        +
3. Офлайн-оценка (replay) любой версии модели на сохранённых размеченных
   событиях → сохранённые отчёты → сравнение версий бок о бок
```

Главный принцип из PROJECT_BRIEF.md: приоритет метрик — FAR, затем FRR, затем
доля uncertain, затем латентность, затем accuracy. Событие (проход) — минимальная
единица оценки: метрики считаются по событиям, а не по отдельным кадрам.

Единый словарь решений identity по событию:

- `known:<имя>` — уверенность по лучшим кадрам достигла порога;
- `uncertain` — кот есть, но порог не достигнут;
- `no_prediction` — модель не запускалась (нет кадров с котом и т.п.).

Определения метрик (по размеченным событиям, согласованы с
`training/acceptance.py::calculate_metrics`):

- FAR — доля событий `foreign_cat`, получивших `known:<любое имя>`;
- FRR — доля событий `known_cat`, не получивших `known:<их имя>`;
- отдельным счётчиком — `misidentified_known`: событие `known_cat`, получившее
  `known:<чужое имя>` (входит в FRR, но выводится отдельно);
- uncertain rate — доля `uncertain` среди всех оценённых событий;
- detection miss — доля размеченных событий с котом, где детектор
  соответствующей камеры ни разу не достиг рабочего порога.

## Фаза 1. Реестр моделей и предсказания по событиям

Миграции SQLite (новые файлы в `src/common/migrations/`):

- `model_versions`: id, kind (`detector` | `identity_face` | `identity_side`),
  file_name, sha256 (уникальный), metadata JSON (labels, image_size),
  first_seen_at. Recorder при загрузке моделей регистрирует их по sha256
  (повторная загрузка той же модели не создаёт дубликат).
- `event_predictions`: id, event_id (FK), model_version_id (FK), view,
  origin (`online` | `evaluation`), evaluation_run_id (FK, NULL для online),
  decision, predicted_name, confidence, frames_used, max_detector_confidence,
  mean_inference_ms, created_at.

Recorder при публикации автоматического события сохраняет по одной online-записи
на каждый ракурс с активной identity-моделью: агрегат по кадрам события
(имя — большинством среди кадров выше порога, confidence — максимум победителя).
Сейчас предсказания живут только в heartbeat (`identity_predictions` в
`src/recorder/app.py`) — накопление за время события и сброс при publish нужно
добавить рядом с `active_confidences`.

В API событий и в списке событий админки показывай предсказание рядом с ручной
меткой: «Модель: Барсик 0.91 / Разметка: Барсик» — оператор сразу видит ошибки.

## Фаза 2. Общий модуль метрик

Вынеси чистую логику метрик в `src/common/metrics.py`:

- перенеси `calculate_metrics` и `AcceptanceMetrics` из `training/acceptance.py`
  (в `training.acceptance` оставь реимпорт для обратной совместимости);
- добавь `misidentified_known` в счётчики;
- добавь `threshold_sweep(scores, labels, thresholds)`: по сохранённым сырым
  (имя, confidence) предсказаниям возвращает FAR/FRR/uncertain для сетки
  порогов, например 0.50–0.95 с шагом 0.05 — без повторного инференса;
- добавь агрегацию кадровых предсказаний в решение по событию (та же логика,
  что в recorder, — одна реализация, используемая обоими путями);
- функции чистые, без I/O; покрой юнит-тестами, включая пустые группы
  (нет чужих событий → FAR не определён, must not делить на ноль — вернуть None
  и пометить отчёт непригодным, как это делает `passed` в acceptance).

## Фаза 3. Офлайн-оценка на сохранённых событиях

Отдельный процесс по образцу `training/local_job.py` (запуск из админки,
detached, статус в JSON, лог локально):

- вход: фильтр событий (диапазон дат, метки `known_cat`/`foreign_cat`,
  training_target) и версии моделей — активные или явно указанные пары
  `.onnx` + `.json` из локального каталога `models/`;
- для каждого события: извлечь кадры (переиспользуй
  `training/workflow.py::extract_frames` и кроп из
  `src/inference/preprocessing.py` — тот же контракт, что у recorder), прогнать
  детектор и identity через OpenVINO CPU, агрегировать в решение по событию;
- записать `evaluation_runs` (id, created_at, фильтр JSON, model_version_id по
  ракурсам, статус, metrics JSON) и `event_predictions` с origin=`evaluation`,
  включая сырые confidence — они нужны для threshold sweep;
- в metrics JSON: FAR, FRR, misidentified_known, uncertain rate, accuracy,
  confusion по именам, метрики по каждому ракурсу отдельно, mean_inference_ms,
  threshold sweep; отдельно — число событий, «видевшихся» в обучении
  (training_target в `macbook`/`local`) и метрики только по «чистым» событиям:
  сравнение версий честно только на событиях, не участвовавших в обучении;
- events с метками `not_visible`/`multiple_cats`/`pending` в оценку identity не
  входят, но считаются для detection miss (кроме `not_visible`).

## Ограничения реализации

- Метрики и оценки ничего не активируют и не меняют пороги — только показывают;
  активация моделей остаётся отдельной ручной процедурой.
- Не переписывай существующие миграции и не ломай чтение старых баз: новые
  таблицы и колонки — только новыми миграциями.
- Оценочный инференс не должен мешать recorder: отдельный процесс, число
  параллельных инференсов 1, событие обрабатывается за событием.
- В журналы и таблицы не попадают RTSP URL, пароли и изображения.
- После каждой фазы: `python -m ruff check .`, `python -m mypy src training`,
  `python -m pytest` — не переходить дальше при ошибках.
