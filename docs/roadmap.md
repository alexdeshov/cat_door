# План развития проекта

Составлен по итогам аудита 2026-07-30. Отражает текущее состояние: контур
сбора данных замкнут (кольцевой буфер → автособытия → разметка → экспорт →
обучение на MacBook), идентификация экспериментальна, управление дверью
отсутствует. Порядок разделов — рекомендуемый порядок работ.

## Ближайший горизонт (недели)

### 1. Гигиена репозитория

- Слить `feature/local-event-admin` и тренировочные ветки в `main`: сейчас
  рабочий код рассредоточен по трём веткам, а `main` сильно отстаёт.
- Поднять CI (GitHub Actions): ruff, mypy, pytest на каждый push и pull
  request. Тесты существуют, но прогоняются только вручную.

### 2. Данные важнее моделей

- Накопить минимум по 100 независимых событий на каждого домашнего кота и
  отдельный корпус чужих котов (см. PROJECT_BRIEF.md).
- Целенаправленно сохранять и размечать ночные/ИК-проходы — они будут главным
  источником ошибок распознавания.
- В очереди разметки первыми показывать события с низкой уверенностью модели
  (простая форма active learning).
- До накопления датасета не вкладываться в усложнение архитектуры моделей.

### 3. Исправления распознавания Cute 2

Выполняются по `docs/codex-detection-fixes-prompt.md`: пер-камерный гейт
идентификации, кроп по рамке детектора, претрен классификатора, ROI и
пер-камерный FPS, OpenVINO на iGPU, подготовка замены детектора.

- ROI реализован, но по замерам 2026-08-05 на текущих сценах не применяется:
  выигрыша нет ни у одной камеры (см. `docs/cameras.md`, «Разрешение, ROI…»).
- Фазы 1–5 fixes prompt и программный контур фазы 6 реализованы: адаптеры
  NanoDet/YOLOX/YOLO11, безопасная подготовка, CPU latency probe и
  detector-only offline replay описаны в `docs/detector-candidates.md`.
- Фаза 6 не считается принятой до явного скачивания весов, замеров всех
  кандидатов на одних событиях и проверки INT8 лучшей модели; baseline
  автоматически не заменяется.

### 4. Двухуровневая обработка из брифа

- Дежурная детекция остаётся на субпотоке, но после подтверждения события
  брать кадры основного потока в полном разрешении.
- Выбирать 5–10 лучших кадров события по резкости, размеру и положению рамки.
- Идентификацию выполнять по лучшим кадрам, а не по дежурным 320×320.

## Средний горизонт (1–3 месяца)

### 5. Embeddings и честный open-set

- Перейти от closed-set softmax к metric learning (ArcFace/triplet):
  эмбеддинг на кадр → сравнение с центроидами домашних котов по косинусной
  дистанции → порог, откалиброванный по FAR на корпусе чужих котов.
- Добавление нового кота не должно требовать переобучения — только вычисление
  новых центроидов.

### 6. Fusion и решение по событию

- Реализовано накопление identity-предсказаний по серии кадров, сохранение
  event-level решения в SQLite и безопасное правило: конфликт имён камер даёт
  `uncertain`.
- Реализованы скользящие FAR/FRR/uncertain и offline replay с clean-срезом.
- Следующий шаг — взвешенная формула из PROJECT_BRIEF.md с учётом качества
  ракурса: `face_score × face_quality × 0.65 + body_score × body_quality × 0.35`.

### 7. Реестр моделей и приёмка

- Реестр SHA-256, offline replay, отчёты и сравнение версий в админке
  реализованы; контракт описан в `docs/metrics.md`.
- Осталось добавить загрузку полного model package, ручную активацию принятой
  версии и откат. Метрики намеренно ничего не активируют автоматически.

### 8. Эксплуатационная устойчивость

- Watchdog процессов recorder и web.
- Контроль свободного места (минимум 50–80 ГБ) и ретеншн событий (14–30 дней).
- Автоматический бэкап SQLite и каталога `events/` на второй носитель:
  разметка — самый ценный актив проекта, дороже любого кода.

## Дальний горизонт

### 9. Shadow mode как путь к двери

- Длительная работа в режиме «дверь открылась бы» с журналом решений и
  регулярным разбором.
- Формальный критерий перехода к реальной механике записать заранее,
  например: «FAR = 0 на N сотнях подряд событий, включая ночные».

### 10. Контроллер двери

- ESP32 по `docs/esp32-protocol.md`: heartbeat, концевики, безопасный режим
  при потере связи, ручная разблокировка.
- Определение направления движения (вход/выход) по side-камере — без него
  дверь не отличает «кот хочет войти» от «кот сидит рядом».

### 11. Железо

Два несоответствия брифу, которые решаются одной покупкой:

- Cute 2 подключена по Wi-Fi, тогда как бриф требует изолированный проводной
  сегмент для камер;
- Cute 2 смонтирована сверху, тогда как роль `face` требует ракурса на уровне
  головы кошки.

Запланированная уличная 4 Мп PoE-камера, установленная на уровне головы,
устраняет обе проблемы и даст качеству идентификации больше, чем замена
нейросети.

### 12. Расширение за пределы кошачьего контура

Камеры у калиток с распознаванием лиц, автоматика замков и видеоаналитика
перемещений описаны отдельно в `docs/expansion-plan.md`. Ключевые решения:
люди — через готовый Frigate, коты — через собственный контур; общий
вычислительный узел на Intel 12+ gen решает и GPU-проблему котов.

### 13. Качество обнаружения и опознания

Разбор ложных срабатываний, выбор детектора и переход опознания на эмбеддинги
описаны отдельно в `docs/detection-quality-plan.md`. Там же — замеры, которые
не надо повторять: встроенное видеоядро для инференса в 5.6 раза медленнее
процессора, а для декодирования даёт десятикратную экономию.

## Общий принцип

Замкнутый цикл данных уже есть. Каждый новый слой (fusion, приёмка, shadow
mode) должен сам генерировать измеримые метрики, а не полагаться на разовые
эксперименты. При сомнении система не открывает дверь и сохраняет событие для
проверки.
