# Развёртывание на Ubuntu Server

> **Документ в работе.** Здесь описан только ввод машины в строй и получение
> удалённого доступа. Разделы про systemd-юниты, `sd_notify`, каталог `install/`
> и раскладку `/opt/catdoor` плюс `/var/lib/catdoor` появятся вместе с PR 2
> плана переноса. Состояние кода: `main` уже POSIX-only, Windows-моноблок
> заморожен на теге `windows-runtime-final`.

Целевая машина — mini-PC, на который переезжает runtime с Windows-моноблока.
Тот же узел планируется под контур калиток из отдельного репозитория
`gate_access`, поэтому сеть и доступ настраиваются один раз для обоих проектов.

Адреса, логины и пароли в этот документ не записываются. Ниже используются
подстановки `<IP-мини-PC>`, `<IP-мака>` и `<логин>`.

## Первая загрузка

После установки Ubuntu Server последним на консоли остаётся вывод `cloud-init`
с отпечатками SSH host-ключей машины (`SHA256:...` для `ed25519` и `ecdsa`).
Это нормальное завершение установки, а не ошибка: просто вывод закончился, а
приглашение `login:` уехало вверх либо экран погас.

Отпечатки печатаются один раз. Их следует сфотографировать до очистки экрана —
именно с ними сверяется значение, которое SSH покажет при первом подключении.

Дальше на самой машине:

```sh
# Enter — появится приглашение login:
ip -4 a          # адрес физического интерфейса: enp... или eno...
ip r             # шлюз по умолчанию
```

Адрес нужно брать со строки физического интерфейса. Значения с `lo`, `docker0`
и `virbr0` для удалённого доступа непригодны.

## Проверка SSH: сокет-активация

Начиная с Ubuntu 22.10 SSH работает через сокет-активацию. Порт слушает
`ssh.socket`, а `ssh.service` остаётся неактивным до первого подключения.

Поэтому `systemctl is-active ssh` штатно отвечает `inactive` на исправной
машине. Это не признак поломки. Проверять нужно сокет и фактического слушателя:

```sh
systemctl is-active ssh.socket
ss -tlnp | grep ':22'
```

Ожидается `active` и слушатель на `0.0.0.0:22` или `*:22`.

Косвенный признак того, что `openssh-server` установлен: отпечатки host-ключей
на экране первой загрузки. Без пакета они не генерируются. Если слушателя всё
же нет:

```sh
sudo apt update && sudo apt install -y openssh-server
sudo systemctl enable --now ssh
```

## Диагностика недоступности с мака

Симптом определяет причину точнее, чем любые дальнейшие проверки:

| Что видно с мака | Что это значит |
| --- | --- |
| `Connection refused` сразу | Хост доступен, но на 22-м порту никто не слушает. Проблема в `openssh-server`. |
| Зависание на `Connecting to ... port 22` | Пакеты дропаются молча. До SSH дело не доходит, проблема сетевая. |
| Запрос отпечатка или пароля | Связь есть, дальше вопрос аутентификации. |

Разделять эти случаи следует до любых действий:

```sh
ssh -v <логин>@<IP-мини-PC>     # где именно застревает
ping -c 3 <IP-мини-PC>          # отвечает ли хост вообще
ipconfig getifaddr en0          # своя подсеть
netstat -rn | grep default      # свой шлюз
```

### Молчаливое зависание: четыре причины

Проверять в этом порядке — от самой дешёвой проверки к самой дорогой.

1. **`ufw` режет порт.** Он именно DROP'ает пакеты, а не отвечает отказом,
   отсюда тишина вместо `Connection refused`.
   Проверка — `sudo ufw status`. Если `active`, то `sudo ufw allow OpenSSH`.
2. **Адрес неверный.** Взят с виртуального интерфейса либо уже сменился по
   DHCP. Проверка — `ip -4 a` на машине.
3. **Разные подсети.** Первые три октета у мака и у мини-PC должны совпадать.
   Расхождение означает лишний роутер между устройствами: домашние роутеры
   раздают одну подсеть, а вторая появляется, когда за первым роутером включён
   второй со своим NAT. Из верхней сети нижняя недостижима.
   Проверка — сравнить `ip -4 a` с `ipconfig getifaddr en0`, а `ip r` со шлюзом
   мака.
4. **Изоляция клиентов на Wi-Fi (AP isolation).** Роутер запрещает устройствам
   в своей сети общаться напрямую. Характерный признак: подсети совпадают, но
   ICMP не проходит. Проверка — подключить мак кабелем в ту же сеть; если
   заработало, дело в изоляции.

Отдельно на маке стоит убедиться, что не поднят VPN: он часто заворачивает весь
трафик, включая обращения к локальным адресам.

### Если подсети разные

Правильное решение — физически перенести мини-PC в ту же сеть, где находятся
мак и остальные устройства: переставить кабель в роутер или свитч верхнего
уровня. Пробрасывать порты через двойной NAT ради домашнего сервера смысла нет.

Это не косметическое требование. Админка CatDoor выставляется в LAN без
аутентификации и ограничивается правилом `ufw`, а камеры и мини-PC должны
находиться в одной сети. Двойной NAT ломает эту схему целиком, поэтому вопрос
с подсетью закрывается до начала развёртывания сервисов.

## Базовая настройка после получения доступа

```sh
sudo apt update && sudo apt full-upgrade -y
sudo timedatectl set-timezone Europe/Moscow
sudo systemctl mask sleep.target suspend.target hibernate.target hybrid-sleep.target
```

Маскирование целей сна обязательно: узел работает круглосуточно и должен
переживать отсутствие сессии. За машиной следует закрепить постоянный адрес —
проще всего резервацией по MAC на роутере, чтобы адрес не менялся после
перезагрузки и не ломал ссылки на админку.
