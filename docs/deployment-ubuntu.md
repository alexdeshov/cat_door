# Развёртывание на Ubuntu Server

> **Документ в работе.** Ввод машины в строй, доступ по SSH и запуск служб
> описаны. Состояние кода: `main` уже POSIX-only, Windows-моноблок заморожен на
> теге `windows-runtime-final`.

Целевая машина — mini-PC, на который переезжает runtime с Windows-моноблока.
Тот же узел планируется под контур калиток из отдельного репозитория
`gate_access`, поэтому сеть и доступ настраиваются один раз для обоих проектов.

Адреса, логины и пароли в этот документ не записываются. Ниже используются
подстановки `<IP-мини-PC>`, `<IP-мака>` и `<логин>`.

## Первая загрузка

После установки Ubuntu Server последним на консоли остаётся вывод `cloud-init`
с отпечатками SSH host-ключей машины (`SHA256:...` для `ed25519` и `ecdsa`).
Это нормальное завершение установки, а не ошибка: просто вывод закончился, а
приглашение `login:` уехало вверх либо экран погас.

Отпечатки печатаются один раз. Их следует сфотографировать до очистки экрана —
именно с ними сверяется значение, которое SSH покажет при первом подключении.

Дальше на самой машине:

```sh
# Enter — появится приглашение login:
ip -4 a          # адрес физического интерфейса: enp... или eno...
ip r             # шлюз по умолчанию
```

Адрес нужно брать со строки физического интерфейса. Значения с `lo`, `docker0`
и `virbr0` для удалённого доступа непригодны.

## Проверка SSH: сокет-активация

Начиная с Ubuntu 22.10 SSH работает через сокет-активацию. Порт слушает
`ssh.socket`, а `ssh.service` остаётся неактивным до первого подключения.

Поэтому `systemctl is-active ssh` штатно отвечает `inactive` на исправной
машине. Это не признак поломки. Проверять нужно сокет и фактического слушателя:

```sh
systemctl is-active ssh.socket
ss -tlnp | grep ':22'
```

Ожидается `active` и слушатель на `0.0.0.0:22` или `*:22`.

Косвенный признак того, что `openssh-server` установлен: отпечатки host-ключей
на экране первой загрузки. Без пакета они не генерируются. Если слушателя всё
же нет:

```sh
sudo apt update && sudo apt install -y openssh-server
sudo systemctl enable --now ssh
```

## Диагностика недоступности с мака

Симптом определяет причину точнее, чем любые дальнейшие проверки:

| Что видно с мака | Что это значит |
| --- | --- |
| `Connection refused` сразу | Хост доступен, но на 22-м порту никто не слушает. Проблема в `openssh-server`. |
| Зависание на `Connecting to ... port 22` | Пакеты дропаются молча. До SSH дело не доходит, проблема сетевая. |
| Запрос отпечатка или пароля | Связь есть, дальше вопрос аутентификации. |

Разделять эти случаи следует до любых действий:

```sh
ssh -v <логин>@<IP-мини-PC>     # где именно застревает
ping -c 3 <IP-мини-PC>          # отвечает ли хост вообще
ipconfig getifaddr en0          # своя подсеть
netstat -rn | grep default      # свой шлюз
```

### Молчаливое зависание: четыре причины

Проверять в этом порядке — от самой дешёвой проверки к самой дорогой.

1. **`ufw` режет порт.** Он именно DROP'ает пакеты, а не отвечает отказом,
   отсюда тишина вместо `Connection refused`.
   Проверка — `sudo ufw status`. Если `active`, то `sudo ufw allow OpenSSH`.
2. **Адрес неверный.** Взят с виртуального интерфейса либо уже сменился по
   DHCP. Проверка — `ip -4 a` на машине.
3. **Разные подсети.** Первые три октета у мака и у мини-PC должны совпадать.
   Расхождение означает лишний роутер между устройствами: домашние роутеры
   раздают одну подсеть, а вторая появляется, когда за первым роутером включён
   второй со своим NAT. Из верхней сети нижняя недостижима.
   Проверка — сравнить `ip -4 a` с `ipconfig getifaddr en0`, а `ip r` со шлюзом
   мака.
4. **Изоляция клиентов на Wi-Fi (AP isolation).** Роутер запрещает устройствам
   в своей сети общаться напрямую. Характерный признак: подсети совпадают, но
   ICMP не проходит. Проверка — подключить мак кабелем в ту же сеть; если
   заработало, дело в изоляции.

Отдельно на маке стоит убедиться, что не поднят VPN: он часто заворачивает весь
трафик, включая обращения к локальным адресам.

### Если подсети разные

Правильное решение — физически перенести мини-PC в ту же сеть, где находятся
мак и остальные устройства: переставить кабель в роутер или свитч верхнего
уровня. Пробрасывать порты через двойной NAT ради домашнего сервера смысла нет.

Это не косметическое требование. Админка CatDoor выставляется в LAN без
аутентификации и ограничивается правилом `ufw`, а камеры и мини-PC должны
находиться в одной сети. Двойной NAT ломает эту схему целиком, поэтому вопрос
с подсетью закрывается до начала развёртывания сервисов.

## Базовая настройка после получения доступа

```sh
sudo apt update && sudo apt full-upgrade -y
sudo timedatectl set-timezone Europe/Moscow
sudo systemctl mask sleep.target suspend.target hibernate.target hybrid-sleep.target
```

Маскирование целей сна обязательно: узел работает круглосуточно и должен
переживать отсутствие сессии. За машиной следует закрепить постоянный адрес —
проще всего резервацией по MAC на роутере, чтобы адрес не менялся после
перезагрузки и не ломал ссылки на админку.

## Раскладка на диске

| Путь | Что там | Владелец |
| --- | --- | --- |
| `/opt/catdoor` | рабочая копия репозитория и `.venv` | обычный пользователь |
| `/var/lib/catdoor` | база, видео, кольцевой буфер, runtime-файлы | `catdoor` |
| `/etc/catdoor/catdoor.env` | конфигурация служб | `root:catdoor`, режим 640 |
| `/etc/systemd/system/catdoor-*.service` | юниты | root |

Видео живёт на отдельной файловой системе, а не на корне. Переполнение корня
валит journald, SQLite и systemd целиком, и чинить это придётся с монитором и
клавиатурой; переполнение отдельного тома ломает только запись.

Конфигурация лежит в `/etc`, а не в `.env` рядом с кодом: там её не затирает
`git pull` и не видит никто, кроме root и служебного пользователя. В файле
находится RTSP-пароль камеры — но только для первого запуска.

Режим автоматического сбора переключается на главной странице админки и
хранится в `/var/lib/catdoor/runtime/capture-mode.json`. Переменные
`CATDOOR_AUTOMATIC_CAPTURE_ENABLED` и `CATDOOR_AUTOMATIC_CAPTURE_DRY_RUN`
задают только начальное положение; после первого переключения они не читаются.
Recorder подхватывает смену в течение секунды и без перезапуска.

Инвентарь камер живёт в `/var/lib/catdoor/runtime/cameras.json` с правами
`0600` и владельцем `catdoor`. Он создаётся при первом старте из переменных
`CATDOOR_CAMERA_*`, после чего адреса, учётные данные и роли правятся на
вкладке «Камеры» без перезапуска служб. Переменные окружения после этого не
перечитываются. Файл содержит пароли камер: он не попадает ни в Git, ни в
экспорт датасета, и при резервном копировании требует того же обращения, что и
`/etc/catdoor/catdoor.env`.

## Установка служб

```sh
cd /opt/catdoor
python3 -m venv .venv
.venv/bin/pip install -e '.[dev]'
.venv/bin/pytest
sudo ./install/install.sh
```

Скрипт идемпотентен: создаёт системного пользователя `catdoor`, назначает ему
том с данными, ставит юниты и включает их. Существующий
`/etc/catdoor/catdoor.env` он не перезаписывает, службы не запускает — обновление
не должно перезапускать recorder в середине события.

Дальше заполнить камеры и запустить:

```sh
sudo nano /etc/catdoor/catdoor.env
sudo systemctl start catdoor-recorder catdoor-web
systemctl status catdoor-recorder --no-pager
journalctl -u catdoor-recorder -n 30
```

## Что заменил systemd

Раньше живучестью занимался `scripts/watchdog.py`: отдельный процесс проверял
свежесть статуса recorder и HTTP-ответ админки, считал попытки перезапуска,
выдерживал паузу и уходил в backoff. Это 276 строк, повторяющих штатные
возможности systemd, и с врождённым дефектом — супервизор мог умереть вместе с
тем, что он сторожит.

| Прежняя настройка | Замена в юните |
| --- | --- |
| `watchdog_recorder_stale_seconds=180` | `WatchdogSec=60` |
| `watchdog_restart_cooldown_seconds=600` | `RestartSec=5` плюс `RestartSteps=5` |
| `watchdog_max_restart_attempts=3` | нет — служба не сдаётся |
| `watchdog_failure_backoff_seconds=1800` | `RestartMaxDelaySec=1800` |
| `watchdog_web_timeout_seconds` | нет — вместо HTTP-пробы пинг `sd_notify` |

Вместо «три попытки, потом получасовая блокировка» получился экспоненциальный
backoff от 5 секунд до 30 минут без потолка попыток. Для узла, который работает
без присмотра, это лучше: он не остаётся навсегда в `failed` после серии сбоев.

`RestartSteps` и `RestartMaxDelaySec` появились в systemd 254, Ubuntu 24.04
несёт 255. Установщик проверяет версию и отказывается работать на более старой.

`StartLimitIntervalSec=0` задан явно. По умолчанию systemd после пяти запусков
за десять секунд оставляет юнит в `failed` — то есть обещание «служба не
сдаётся» держалось бы лишь на том, что `RestartSec` больше этого окна.

## Контур калитки и примиритель

Какой контур работает, решает переключатель в админке; он записывает выбор в
`/var/lib/catdoor/runtime/circuits.json`. Приводит службу Frigate к этому
выбору отдельная пара юнитов:

```sh
sudo cp install/catdoor-gate-sync.service install/catdoor-gate-sync.path \
        /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now catdoor-gate-sync.path
sudo systemctl enable catdoor-gate-sync.service
```

`.path` следит за файлом и запускает `.service` при каждом изменении;
`enable` у самой службы нужен для одного прогона при загрузке — контейнер
Frigate объявлен с `restart: "no"`, и без этого узел, отданный калитке,
поднялся бы с остановленным контуром.

Третий юнит — `.timer`, регулярная сверка раз в две минуты. Она закрывает два
класса отказов, которые событийная схема не видит: фронт изменения файла,
пришедший во время прогона примирителя, systemd не ставит в очередь и теряет;
а контейнер под oneshot-юнитом с `RemainAfterExit` может умереть, оставив юнит
«работающим», — примиритель сверяет контейнер с юнитом через Docker и
перезапускает службу. Юниты примирителя ставит `install.sh`, отдельной ручной
установки больше нет.

Управлять службой из веб-процесса нельзя: в его юните стоит
`NoNewPrivileges=true`, поэтому `sudo` оттуда не работает. Это не обходится
правилом `sudoers` — и не должно: у админки нет аутентификации, а значит и
привилегий у неё быть не должно.

Проверка:

```sh
systemctl status catdoor-gate-sync.path --no-pager | head -4
journalctl -u catdoor-gate-sync -n 5 --no-pager
```

### Что стартует при загрузке

| Юнит | В автозапуске | Что делает |
| --- | --- | --- |
| `catdoor-recorder` | да | кошачий контур; сам смотрит, разрешён ли он узлу |
| `catdoor-web` | да | админка |
| `dnsmasq` | да | адреса камерам |
| `docker` | да | нужен контуру калитки |
| `catdoor-gate-sync.path` | да | следит за файлом состояния |
| `catdoor-gate-sync.service` | да | один прогон при загрузке |
| `frigate` | **нет** | поднимается только примирителем |

`frigate.service` намеренно не в автозапуске, а его контейнер объявлен с
`restart: "no"`: иначе Docker поднимал бы контур калитки при каждой загрузке
независимо от того, какой контур выбран, и переключатель терял бы смысл.

## Что происходит при отключении питания

Проверять восстановление имеет смысл по трём отдельным сценариям — они ломаются
по-разному.

**Диск.** Свободное место тома данных видно в строке состояния админки; ниже
порога `CATDOOR_DISK_MIN_FREE_GB` (по умолчанию 2 ГБ) новые записи не
начинаются — и автоматические, и ручные — с явным отказом, а не тихим
исчезновением проходов. Заполненный до конца диск глушил бы и сами записи, и
всю отчётность о них: статус, журнал, базу. Записи со статусом «идёт запись»,
прерванные отключением, при старте recorder помечаются отказом; экспорты для
MacBook хранятся последние три.

**Пропало питание на сервере.** Обе службы включены в автозапуск и поднимаются
без участия владельца; проверено реальной перезагрузкой. База в режиме WAL
переживает жёсткое выключение без разрушения, теряются только последние
незаписанные транзакции. Инвентарь камер и настройки детекции пишутся через
временный файл с `fsync` файла и каталога перед подменой имени: без этого
переименование могло пережить обрыв раньше данных и оставить файл нулевой
длины, то есть стереть адреса и пароли камер. Незавершённые `.part.mp4`,
`.concat.txt`, временные файлы настроек и пустые сегменты кольцевого буфера
удаляются при старте recorder — блоки `finally` при пропаже питания не
исполняются.

**Пропало питание на камере.** Если камера возвращается на тот же адрес, роль
переподключается сама в течение `CATDOOR_CAMERA_STALL_SECONDS`. Если она
возвращается с новой арендой DHCP, recorder сверяет молчащие камеры с
`dnsmasq.leases` по MAC и подставляет новый адрес самостоятельно, записывая в
журнал детекции `camera_address_recovered`. Меняется только адрес: пароль, роль
и путь потока к смене аренды отношения не имеют. Камере без заполненного MAC
адрес не правится — совпадение недоказуемо, а чужой адрес хуже неработающего.

**Камера исчезла, не закрыв соединение.** Самый неприятный случай: процесс
ffmpeg остаётся живым и молчит, а чтение кадра блокирующее. Главный цикл при
этом работает и исправно кормит watchdog, поэтому systemd такой отказ не видит.
Recorder следит за временем последнего кадра каждой роли и, если кадров нет
дольше `CATDOOR_CAMERA_STALL_SECONDS`, убивает процесс — чтение возвращает
конец файла, и роль подключается заново. В журнале это `stream_stalled`.

Что при этом проверять после восстановления питания:

```sh
systemctl is-active catdoor-recorder catdoor-web dnsmasq
sudo tail -5 /var/lib/catdoor/runtime/detection.jsonl
sudo cat /var/lib/catdoor/runtime/recorder-status.json
```

В статусе раздел `cameras` показывает по каждой роли, назначена ли камера и
задан ли адрес; события `stream_stalled` и `camera_address_recovered` в журнале
детекции говорят, что восстановление действительно отработало.

## Как проверить, что sd_notify работает

Обе службы объявлены как `Type=notify`. Это значит, что systemd держит юнит в
состоянии `activating (start)` до тех пор, пока процесс не пришлёт `READY=1`.

- `active (running)` — рукопожатие состоялось;
- зависание в `activating (start)` с последующим таймаутом — `READY=1` не дошёл;
- у recorder признак жизни виден в `systemctl show catdoor-recorder -p StatusText`.

Recorder шлёт пинг в тот же момент, когда публикует статус для админки, то есть
не реже раза в пять секунд. Админка шлёт пинг из фоновой задачи на event loop,
поэтому заблокированный цикл гасит пинг даже при живом процессе.

Проверка восстановления:

```sh
sudo systemctl kill -s SIGKILL catdoor-recorder
systemctl show catdoor-recorder -p NRestarts -p MainPID
journalctl -u catdoor-recorder -n 8 --no-pager
```

Счётчик должен вырасти, `MainPID` — смениться, служба вернуться в `active`.

Команда при этом печатает пугающее, но безобидное сообщение:

```
Failed to kill unit catdoor-recorder.service: Failed to send signal SIGKILL
to auxiliary processes: Invalid argument
```

Главный процесс к этому моменту уже убит. Ошибка относится к попытке добить
остальные процессы cgroup, которых у службы нет. Смотреть надо в журнал: там
подряд идут `Sent signal SIGKILL to main process`, `Main process exited,
code=killed, status=9/KILL` и через `RestartSec` секунд `Started`. Если
сообщение мешает, можно бить точечно:

```sh
sudo systemctl kill -s SIGKILL --kill-whom=main catdoor-recorder
```

## Firewall

`ufw` включается только после того, как правило для SSH заведено — иначе
соединение оборвётся вместе с сессией.

```sh
sudo ufw allow OpenSSH
sudo ufw allow from <подсеть-LAN> to any port 8080 proto tcp
sudo ufw enable
sudo ufw status verbose
```

Порт админки открывается именно подсети, а не всему миру. Интерфейс не имеет
аутентификации: он удаляет события и отдаёт потоки с камер. Ограничение по сети
здесь — единственная защита, поэтому `CATDOOR_WEB_HOST=0.0.0.0` допустим только
вместе с этим правилом. Без правила остаётся `127.0.0.1` и SSH-туннель.

## Изолированная сеть камер

Камеры подключены к PoE-коммутатору, который воткнут **только в `eno1`**
мини-PC. Наружу этот сегмент не ведёт: в `docs/cameras.md` изолированная сеть
без доступа в интернет записана как требование, а не как предпочтение.

Схема получается такая:

| Интерфейс | Сеть | Для чего |
| --- | --- | --- |
| `wlp0s20f3` | домашняя LAN | админка, SSH, доступ с мака |
| `eno1` | 192.168.1.0/24, изолированная | камеры |

Обе карты работают одновременно и не конфликтуют, потому что находятся в разных
подсетях. Выключать Wi-Fi при такой топологии не нужно — он остаётся
единственным путём к управлению.

### Постоянный адрес сервера в сети камер

`/etc/netplan/60-catdoor-eno1.yaml`:

```yaml
network:
  version: 2
  ethernets:
    eno1:
      optional: true
      dhcp4: false
      addresses:
        - 192.168.1.10/24
```

`optional: true` обязателен: без него `systemd-networkd-wait-online` задержит
загрузку на полторы минуты, когда кабель не воткнут.

Применять через `sudo netplan try` — команда откатывает изменения через 120
секунд, если не подтвердить. Для правки сети на удалённой машине это
единственный безопасный способ.

### DHCP для камер

Заводская Hikvision сначала просит адрес по DHCP и только потом откатывается на
`192.168.1.64`. Пока сервера нет, все камеры одной модели окажутся на этом
адресе разом и передерутся, поэтому DHCP здесь необходимость.

```sh
sudo apt install -y dnsmasq
sudo cp /opt/catdoor/install/dnsmasq-catdoor-cameras.conf \
        /etc/dnsmasq.d/catdoor-cameras.conf
sudo ufw allow in on eno1 to any port 67 proto udp
echo 'DNSMASQ_EXCEPT="lo"' | sudo tee -a /etc/default/dnsmasq
sudo systemctl restart dnsmasq
```

Камерам выдаётся шлюз — адрес узла. Без него прошивки отвергают аренду и
пропадают из сети, см. `docs/cameras.md`. Дороги наружу это им не даёт:
домашняя сеть ничего не знает про `192.168.1.0/24`, ответить на такой адрес
некому, и ни одно соединение не установится.

**Запрещать маршрутизацию с `eno1` через `sysctl` нельзя.** Выглядит как
очевидное усиление изоляции, а кладёт контур калитки: Frigate ходит к камерам
из контейнера, и ответ камеры возвращается ему через маршрутизацию узла.
С `net.ipv4.conf.eno1.forwarding=0` Frigate получает `Connection timed out` на
все камеры разом, а `curl` с самого узла при этом отвечает как ни в чём не
бывало — проверено 5 августа. Понадобится настоящий запрет — заводить его
правилом `ufw route deny in on eno1 out on <интерфейс домашней сети>`, которое
бьёт по паре интерфейсов и контейнеров не касается.

Правило `ufw` обязательно и легко забывается: DHCP-запрос приходит **входящим**
пакетом, а политика по умолчанию его отбрасывает. Без правила камеры молча не
получат адреса.

Две записи в журнале при установке выглядят отказом, но им и положено там быть:

- `failed to create listening socket for port 53: Address already in use` —
  пакет пытается запустить службу сразу после распаковки, когда конфига с
  `port=0` в `/etc/dnsmasq.d/` ещё нет, и упирается в `systemd-resolved`.
  Следующий запуск, уже с конфигом, проходит штатно;
- `resolvconf: Failed to set DNS configuration: Link lo is loopback device` —
  обвязка пакета пытается зарегистрировать dnsmasq системным резолвером, то
  есть ровно то, что здесь отключено намеренно. `DNSMASQ_EXCEPT="lo"` выше
  убирает эту строку, чтобы через полгода она не сошла за настоящую ошибку.

Запуск удался, если в журнале есть `DNS disabled` и
`sockets bound exclusively to interface eno1`, а `ss -lunp` показывает только
`0.0.0.0%eno1:67`.

### Время для камер

Часы камер сами по себе не выставятся никогда: заводской NTP смотрит в
интернет, а из сети камер туда хода нет. HiWatch так и живёт в 1970 году,
Dahua — в 2000-м, и это видно в кадре: HiWatch вжигает штамп времени в
изображение, а Frigate раскладывает записи по времени события.

Сервером времени становится узел — единственный, кто стоит в обеих сетях:

```sh
sudo apt-get install -y chrony
sudo cp /opt/catdoor/install/chrony-catdoor-cameras.conf \
        /etc/chrony/conf.d/catdoor-cameras.conf
sudo ufw allow in on eno1 to any port 123 proto udp
sudo systemctl restart chrony
chronyc sources
```

Пакет `chrony` вытесняет `systemd-timesyncd` — это штатно и ожидаемо:
`timesyncd` умеет только спрашивать время, а раздавать его не умеет вовсе.

Адрес сервера камеры получают опцией 42 в аренде DHCP, но камере со статикой
его нужно указать руками — команды для обеих платформ приведены в
`docs/cameras.md`, пункт 5 порядка подключения. Проверяется с узла: время в
ответе камеры должно совпадать с `date` секунда в секунду.

### Температура: турбо-частоты запрещены

Узел несёт три контура круглосуточно — работа для процессора есть всегда, и
без ограничения он сидит на турбо-частоте безвылазно. Замер 2026-08-05 на
i3-8109U: на 3.6 ГГц пакет держал 85–92°C при пределе 100°C, и счётчики
троттлинга росли; на базовых 3.0 ГГц — 72–77°C, а все конвейеры держат свои
частоты кадров. Последние 20% частоты стоили ~40% мощности впустую.

Запретом занимается юнит `catdoor-cpu-thermal.service` (ставится `install.sh`).
Проверка: `cat /sys/devices/system/cpu/intel_pstate/no_turbo` — должно быть
`1`, температура — в шапке админки. Порог подсветки 85°C: это не предел чипа,
а сигнал посмотреть на охлаждение и пыль.

### Установка Docker ломает DHCP камер

Пакет `docker.io` тянет за собой `ubuntu-fan`, а тот кладёт в каталог dnsmasq
свой файл `/etc/dnsmasq.d/ubuntu-fan` с директивой `bind-interfaces`. Она
несовместима с `bind-dynamic` из конфигурации проекта, и dnsmasq отказывается
стартовать:

```
dnsmasq: cannot set --bind-interfaces and --bind-dynamic
```

Отказ **отложенный**: установка проходит успешно, работающий dnsmasq
продолжает работать, и ломается всё при следующем перезапуске или перезагрузке
— когда связь между причиной и следствием уже не очевидна.

Fan networking — легаси-оверлей Ubuntu для контейнеров, нашему Docker он не
нужен и удаляется без последствий:

```sh
sudo apt-get -s purge ubuntu-fan | grep -A2 REMOVED
sudo apt-get -y purge ubuntu-fan
sudo systemctl restart dnsmasq && systemctl is-active dnsmasq
```

Первая команда проверяет, что за собой пакет ничего не утащит.

`DNSMASQ_EXCEPT="lo"` в `/etc/default/dnsmasq` на это не влияет: узел работает
с обоими сразу — проверено на живой службе после удаления `ubuntu-fan`.
Подозрение на него было, но не подтвердилось.

### Проверять после перезагрузки, а не после установки

Проверять dnsmasq нужно **после перезагрузки**, а не только после установки.
Ручной запуск происходит при давно поднятой сети и потому ничего не доказывает:
при загрузке dnsmasq стартует раньше, чем netplan настраивает `eno1`. С
`bind-interfaces` это заканчивалось `unknown interface eno1` и службой в
`failed`; в конфигурации проекта поэтому стоит `bind-dynamic`, который
переживает интерфейс, появившийся позже себя.

Подключённые камеры видны в арендах:

```sh
cat /var/lib/misc/dnsmasq.leases
journalctl -u dnsmasq -n 30 --no-pager
```

Каждая строка аренды содержит MAC и выданный адрес — так находится камера, у
которой нет ни экрана, ни заранее известного адреса.

Тот же файл читает поиск камер в админке, поэтому службе нужен доступ на
чтение: аренды лежат в `/var/lib/misc/dnsmasq.leases` с правами `644`, менять
их не требуется. Чтобы поиск обходил сеть камер и отправлял ONVIF-пробу с
`eno1`, а не с интерфейса управления, в `/etc/catdoor/catdoor.env` задаётся:

```dotenv
CATDOOR_CAMERA_DISCOVERY_SUBNET=192.168.1.0/24
```

### Постоянные аренды камер

Адрес из пула достаётся тому, кто первым его попросит, поэтому после
перезагрузки камеры могут поменяться местами. Инвентарь это переживает — камера
опознаётся по MAC, и recorder сам подставляет новый адрес, — но каждая смена
стоит нескольких секунд без кадров. Закреплённая аренда убирает и это.

Отдельная тонкость: камера может держать два адреса сразу. Заводская прошивка
нередко оставляет служебные порты на статическом адресе, продолжая при этом
честно брать аренду по DHCP. В поиске такая камера видна на двух адресах, и
рабочий тот, где открыт порт 554. Ломать это не нужно — достаточно закрепить за
её MAC именно рабочий адрес: dnsmasq перестанет считать его свободным и не
выдаст никому другому.

Реквизиты конкретного узла в репозиторий не попадают, поэтому файл создаётся на
месте:

```sh
sudo tee /etc/dnsmasq.d/catdoor-cameras-local.conf > /dev/null <<'EOF'
# Постоянные аренды камер этого узла.
dhcp-host=<MAC камеры>,<адрес>
EOF
sudo systemctl restart dnsmasq
```

MAC берётся из аренд или из результатов поиска в админке. Адрес можно взять и
внутри пула: зарезервированный dnsmasq больше никому не предлагает. Прежние
аренды того же MAC истекут сами.

Чего брать нельзя — заводской адрес (`.64`, `.108`). Резервация закрывает адрес
только от пула самого dnsmasq, а камера, сброшенная к заводским настройкам,
встаёт на него статикой и ни у кого разрешения не спрашивает. Закрепление на
заводском адресе выглядит надёжным до дня, когда рядом окажется вторая камера
того же вендора, — то есть до самого неудобного дня.

**Пул начинается с `192.168.1.180` не случайно.** Ниже лежат заводские адреса,
на которые камеры встают после сброса: `.64` у Hikvision и HiWatch, `.108` у
Dahua — а на платформе Dahua сделаны и Nobelic, и часть камер Ivideon. Пул,
накрывающий такой адрес, — тихая мина: камера с заводской статикой держит его
молча, dnsmasq выдаёт тот же адрес соседке, и узел получает `401` вместо
кадров. Со стороны это выглядит как неверный пароль, см. `docs/cameras.md`.

Если пул на работающем узле поднимается уже после того, как камеры получили
адреса, они переедут при следующем продлении аренды — или сразу, если их
перезагрузить. Инвентарь это переживает: камера опознаётся по MAC, и recorder
подставляет новый адрес сам.

### Доступ к вебморде камеры с мака

Камеры в изолированном сегменте, поэтому напрямую с мака они недоступны. Для
настройки конкретной камеры поднимается туннель:

```sh
ssh -L 8081:192.168.1.101:80 <логин>@<IP-мини-PC>
```

Пока сессия открыта, камера доступна на `http://localhost:8081`. Это осознанная
цена изоляции: чтобы попасть в камеру, нужен доступ к серверу.
