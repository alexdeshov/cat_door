# Промт для тестирования детекторов-кандидатов

Скопируйте текст ниже в новый сеанс Codex на Windows-моноблоке (там есть
OpenVINO, реальная база событий и замеры латентности имеют смысл).

Предусловие: контур метрик из `docs/codex-metrics-prompt.md` реализован и влит
в `main` (таблицы `model_versions`, `evaluation_runs`, offline-оценка в
админке). Если его нет — сначала выполняется тот промт.

~~~text
Ты работаешь с проектом Cat Door AI на целевом Windows-моноблоке. Задача —
подготовить несколько детекторов-кандидатов, прогнать их через контур метрик на
сохранённых размеченных событиях и по измерениям (не по ощущениям) выбрать
замену текущему SSDLite320 MobileNetV3. Это фаза 6 из
`docs/codex-detection-fixes-prompt.md`.

Сначала обязательно полностью прочитай:

1. AGENTS.md
2. docs/metrics.md (если существует — контракт контура метрик)
3. docs/codex-detection-fixes-prompt.md (раздел фазы 6)
4. docs/automatic-capture.md и docs/deployment-windows.md
5. scripts/prepare_cat_detector.py
6. src/inference/cat_detector.py и src/inference/preprocessing.py
7. src/recorder/frames.py

Ограничения:

- всё локально; веса скачиваются один раз, хранятся в `models/` и в Git не
  попадают;
- inference только OpenVINO **CPU**: GPU Iris Plus 655 непригоден (известный
  CISA-баг драйвера, см. docs/deployment-windows.md) — не пытайся включать GPU;
- бюджет латентности детектора: медиана ≤ 70 мс на кадр при текущей нагрузке
  8 FPS (face) + 3 FPS (side); текущий baseline SSDLite — ~49 мс;
- реальная дверь не управляется; активация модели остаётся ручной — этот

- ветка `feature/detector-candidates` от актуального `main`; после каждой фазы

## Кандидаты

Владелец одобрил использование AGPL для домашнего некоммерческого применения,
поэтому тестируются все три. Поле `license` в манифесте каждой модели
обязательно.

1. **NanoDet-Plus-m @416** — Apache-2.0, ~1.5 GFLOPs, создан для CPU;
2. **YOLOX-Nano @416** — Apache-2.0, ~1.1 GFLOPs;
3. **YOLO11n @416** — AGPL-3.0 (Ultralytics), потолок точности;
4. baseline: текущий SSDLite320 MobileNetV3 — участвует во всех сравнениях.

Если конкретный кандидат не удаётся корректно экспортировать за разумное время,
зафиксируй причину в отчёте и продолжай с остальными — не блокируйся.

## Фаза 1. Переменный размер входа детектора

Сейчас вход жёстко 320×320 (`DETECTOR_INPUT_SIZE` в
`src/inference/preprocessing.py`, проверка shape в `cat_detector.py`,
конвейер кадров 640×360). Сделай размер входа свойством модели:

- манифест уже содержит `input.shape` — используй его как источник истины;
- `prepare_detector_frame`, пересчёт координат рамок и превью должны принимать
  размер параметром (по умолчанию — из загруженной модели);
- кадры 640×360 из FFmpeg достаточны для входа 416 c letterbox; сам конвейер
  RTSP не меняй;
- тесты на 320 и 416.

## Фаза 2. Скрипты подготовки и адаптеры выходов

По образцу `scripts/prepare_cat_detector.py` добавь подготовку каждого
кандидата (отдельный скрипт или один с аргументом модели):

- скачивание официальных весов — только явной командой, с проверкой SHA-256
  скачанного файла; экспорт в ONNX локально;
- по возможности включай декодирование и NMS в сам ONNX-граф (у YOLOX есть
  режим decode-in-inference, у Ultralytics — `nms=True`), чтобы runtime
  оставался простым;
- манифест: `architecture`, `license`, `input.shape`, `cat_class_id`, `sha256`;
- в `OpenVinoCatDetector` сохрани текущий интерфейс `detect()`; различия
  форматов выходов оформи адаптерами, выбираемыми по полю `architecture`
  манифеста; для каждого адаптера — тест на заглушке с синтетическим выходом
  (реальные веса в тестах не используются);
- один общий контракт результата: boxes в координатах входа детектора,
  confidence класса `cat`.

## Фаза 3. Замер латентности на целевой машине

Для каждого кандидата: bounded-прогон `python -m src.recorder.app
--probe-seconds 30` с подменой `CATDOOR_DETECTOR_MODEL_PATH`, затем медиана и
p95 `inference_ms` из `detection.jsonl`. Сведи в таблицу вместе с baseline.
Кандидаты с медианой выше 70 мс помечаются как непрошедшие бюджет, но их
метрики качества всё равно измеряются — владельцу нужна полная картина
(например, ради качества можно снизить FPS).

## Фаза 4. Оценка качества на сохранённых событиях

Используй offline-оценку контура метрик. Если она поддерживает только identity,
расширь её режимом сравнения детекторов: прогон кандидата по кадрам
размеченных событий обеих камер и метрики:

- detection miss rate по камерам: доля событий с котом (`known_cat` /
  `foreign_cat`), где детектор ни разу не достиг рабочего порога камеры;
- отдельно miss rate для Cute 2 — главная боль, ради которой всё затевалось;
- false trigger rate: доля событий `not_visible`, где детектор превысил порог;
- распределение максимальных confidence по событиям (для будущей калибровки
  порогов);
- ночные события отдельной строкой, если время события позволяет их выделить.

Каждый прогон сохраняется как evaluation run с версией модели по SHA-256 —
результаты должны быть видны в админке и воспроизводимы.

## Фаза 5. INT8-квантование лучшего кандидата

Для лучшего по фазам 3–4 кандидата подготовь INT8-вариант через NNCF
(post-training quantization на калибровочном наборе из сохранённых кадров).
Учти: на i3-8109U нет VNNI, выигрыш будет умеренным (~1.3–1.5x). Прогони
INT8-вариант через те же фазы 3–4 и покажи дельту качества против FP32 —
если miss rate ухудшился заметно, рекомендация остаётся FP32.
~~~
