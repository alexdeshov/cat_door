# Milestone 01: запись и ручная разметка событий

## 1. Назначение документа

Этот документ описывает архитектуру и порядок разработки первого milestone CatDoor AI.
Milestone создаёт основу для сбора данных с двух установленных RTSP-камер, но не
включает нейросетевой инференс и не управляет реальной дверью.

Результатом milestone должно стать локальное приложение, которое позволяет:

1. настроить камеры морды и бокового вида;
2. проверить доступность и параметры обоих RTSP-потоков;
3. вручную запустить синхронную запись события;
4. сохранить метаданные события в SQLite, а медиафайлы — в файловой системе;
5. просмотреть событие в локальной веб-админке;
6. вручную разметить событие;
7. экспортировать выбранные размеченные события в ZIP.

Документ является планом. Он не фиксирует детали реализации, которые должны быть
подтверждены отдельными небольшими изменениями и тестами.

## 2. Ограничения milestone

На всём протяжении milestone действуют следующие ограничения:

- только локальная обработка и локальное хранение;
- никакого облачного инференса или отправки кадров во внешние сервисы;
- никакого RFID, NFC, ошейников или имплантируемых меток;
- никакого управления дверью, ESP32, Arduino или силовой механикой;
- режим системы всегда тестовый;
- RTSP URL, имена пользователей и пароли не попадают в Git, SQLite, ZIP и логи;
- адреса камер и пути хранения не зашиваются в код;
- runtime должен работать на Windows и не зависеть от среды обучения на macOS;
- остановка веб-интерфейса не должна останавливать RTSP-подключения или уже
  начатую запись события;
- медиафайлы не хранятся в SQLite;
- изменения схемы SQLite выполняются только через миграции.

## 3. Что входит в milestone

### 3.1. Входит

- две логические роли камер: `face` и `side`;
- локальная настройка основного и, при наличии, дополнительного RTSP-потока;
- безопасное хранение локальной конфигурации вне репозитория;
- ручная и автоматическая проверка соединения;
- состояние соединения и переподключение после разрыва;
- ручной запрос на запись события фиксированной настраиваемой длительности;
- запись двух потоков в общий каталог события;
- измерение фактического временного рассогласования записей;
- SQLite-модель камер, запросов записи, событий, медиа, кошек, разметок и
  экспортов;
- журнал и карточка события;
- справочник домашних кошек, необходимый для ручной разметки;
- разметка события как домашней кошки, чужой кошки, случая без видимой кошки или
  случая с несколькими кошками;
- фоновое формирование ZIP и скачивание готового архива;
- обработка ошибок камеры, записи, базы и файловой системы;
- автоматизированные тесты и приёмочная проверка на целевой Windows-машине.

### 3.2. Не входит

- автоматическое обнаружение кошки;
- модели распознавания, OpenVINO, ONNX Runtime и обучение;
- автоматическое принятие решения `known / unknown / uncertain`;
- управление реальной дверью или симуляция команды контроллеру;
- постоянная полноразмерная видеозапись;
- аппаратная синхронизация камер;
- автоматическое формирование train/validation/test;
- загрузка и активация пакетов моделей;
- доступ к админке из интернета;
- сложная ролевая модель пользователей;
- автоматическое удаление основного датасета.

Если админка будет доступна не только на самом моноблоке, но и в домашней сети,
контроль доступа и сетевое ограничение должны быть согласованы до развёртывания.

## 4. Архитектурные принципы

### 4.1. Разделение процессов

Первый milestone использует как минимум два независимо запускаемых процесса:

- `CatDoorRecorder` — владеет RTSP-подключениями, проверяет состояние камер,
  обрабатывает запросы записи и создаёт медиафайлы;
- `CatDoorWeb` — обслуживает FastAPI, HTML-страницы Jinja2, HTMX-запросы, ручную
  разметку и операции экспорта.

Веб-процесс не должен напрямую владеть долгоживущими RTSP-соединениями. Запрос на
создание события сохраняется в SQLite, после чего `CatDoorRecorder` забирает его
из очереди. Поэтому перезапуск `CatDoorWeb` не прерывает активную запись.

Для milestone допускается один экземпляр каждого процесса. Поддержка нескольких
экземпляров recorder или нескольких Uvicorn workers не требуется.

### 4.2. Поток данных

```text
Локальная конфигурация
        │
        ├───────────────┐
        ▼               ▼
CatDoorRecorder     CatDoorWeb
        │               │
        │ читает очередь│ создаёт запрос записи
        │ из SQLite     │ и разметку
        ▼               ▼
   две RTSP-камеры ── SQLite
        │               │
        ▼               │
 файловая система ◄─────┤ журнал и карточка события
        │               │
        └──────────────►│ ZIP-экспорт
```

SQLite является хранилищем состояния и координации, но не каналом для видеоданных.
Частые покадровые операции в базе запрещены.

### 4.3. Работа при отказах

- Потеря одной камеры не останавливает мониторинг второй.
- Потеря веб-процесса не останавливает recorder.
- Потеря recorder отображается в админке как устаревший heartbeat.
- Незавершённый файл пишется во временный каталог и не считается готовым медиа.
- Событие не получает статус `ready`, пока не проверены ожидаемые файлы.
- После перезапуска процессы находят зависшие запросы и переводят их в
  восстанавливаемое или явно ошибочное состояние.
- Ошибка одного события не останавливает обработку следующих запросов.

## 5. Компоненты

### 5.1. Конфигурация

Должны быть предусмотрены отдельные настройки для ролей `face` и `side`:

- отображаемое имя;
- признак включения;
- основной RTSP URL;
- дополнительный RTSP URL, если он поддерживается камерой;
- предпочитаемый транспорт RTSP, по умолчанию TCP;
- тайм-аут подключения и чтения;
- длительность ручного события;
- параметры повторного подключения;
- корневой каталог данных;
- минимальный допустимый объём свободного места;
- адрес и порт локальной веб-админки.

Основной поток используется для записи события. Дополнительный поток используется
для дешёвой проверки состояния, если он настроен; иначе проверяется основной.

Секретные параметры должны храниться в локальном runtime-конфиге вне Git.
Интерфейс настройки:

- не показывает сохранённый пароль;
- воспринимает пустое поле пароля как «не изменять»;
- маскирует учётные данные в сообщениях об ошибках;
- выполняет валидацию до сохранения;
- записывает конфигурацию атомарно;
- сообщает, было ли подключение перезапущено с новой конфигурацией.

Для milestone допустим локальный файл с ограниченными правами доступа. Возможный
переход на Windows Credential Manager рассматривается отдельно и не должен
блокировать первый milestone.

### 5.2. RTSP и состояние камеры

Для каждой камеры recorder запускает независимый worker с конечным автоматом:

```text
unconfigured → connecting → online
                      │         │
                      ▼         ▼
                    offline ← degraded
                      │
                      └────────→ connecting
```

Состояния:

- `unconfigured` — обязательные параметры отсутствуют;
- `disabled` — камера отключена настройкой;
- `connecting` — выполняется подключение или проверка;
- `online` — поток открывается и декодируются кадры;
- `degraded` — поток доступен, но есть тайм-ауты, пропуски или нестабильность;
- `offline` — поток недоступен после тайм-аута.

Проверка соединения должна подтверждать не только открытие TCP-сокета, но и
получение декодируемых видеоданных. Результат проверки содержит:

- состояние;
- время проверки;
- время до первого кадра;
- разрешение;
- заявленную или измеренную частоту кадров;
- кодек;
- безопасный код ошибки без RTSP URL и пароля.

После ошибки используется ограниченная экспоненциальная задержка с jitter.
Пользовательская команда «проверить сейчас» не должна создавать параллельные
подключения к уже проверяемой камере.

Медиа-backend должен быть изолирован интерфейсом, чтобы в тестах использовать
поддельный источник. Базовым кандидатом для Windows является локальный
FFmpeg/ffprobe: окончательный выбор и способ его поставки подтверждаются отдельным
техническим исследованием до реализации записи.

### 5.3. SQLite

Для доступа к SQLite предполагаются SQLAlchemy 2.x и отдельный инструмент
миграций. При запуске включаются:

- foreign keys;
- WAL, если он стабилен на целевой локальной файловой системе;
- `busy_timeout`;
- короткие транзакции без файловых и сетевых операций внутри них.

База должна находиться на локальном диске, а не на сетевой папке. Пути к медиа
хранятся относительно корневого каталога данных.

Предварительный набор таблиц:

#### `cameras`

- идентификатор;
- уникальная роль `face` или `side`;
- отображаемое имя;
- признак включения;
- версия конфигурации;
- время изменения.

RTSP URL и учётные данные в этой таблице не хранятся.

#### `camera_status`

- камера;
- текущее состояние;
- время последней успешной проверки и последнего кадра;
- heartbeat recorder;
- разрешение, FPS и кодек;
- код последней ошибки;
- время обновления.

Обновления состояния ограничиваются разумной частотой, например один раз в
несколько секунд или при изменении состояния.

#### `capture_requests`

- идентификатор запроса;
- время и источник запроса;
- требуемая длительность;
- статус `queued / claimed / recording / completed / failed / cancelled`;
- время захвата recorder;
- связанное событие;
- безопасный код ошибки;
- число попыток.

Recorder должен забирать запрос атомарно, чтобы один запрос нельзя было выполнить
дважды.

#### `events`

- UUID события;
- тип запуска `manual`;
- время создания, начала и окончания;
- статус `recording / ready / partial / failed`;
- измеренное рассогласование камер;
- статус разметки `pending / reviewed`;
- текущий итог разметки;
- ссылка на подтверждённую домашнюю кошку, если применимо;
- комментарий оператора;
- тестовый режим;
- время последнего изменения.

#### `event_media`

- событие и камера;
- тип медиа;
- относительный путь;
- фактическое начало и окончание;
- длительность;
- размер;
- кодек и разрешение;
- SHA-256;
- статус проверки файла.

Для одной пары «событие, камера, тип медиа» должна действовать уникальность.

#### `cats`

- идентификатор;
- отображаемое имя;
- активность;
- время создания и изменения.

Удаление кошки, уже использованной в разметке, запрещается. Вместо этого она
деактивируется.

#### `reviews`

- событие;
- тип разметки;
- кошка для типа `known_cat`;
- необязательный комментарий;
- время создания;
- локальный автор или источник `web`;
- ссылка на предыдущую разметку при исправлении.

История разметки сохраняется. Текущее значение в `events` является денормализованным
указателем для быстрого журнала.

#### `exports` и `export_items`

- идентификатор экспорта;
- фильтры или явно выбранные события;
- статус `queued / processing / ready / failed`;
- относительный путь к архиву;
- размер и SHA-256;
- время создания и завершения;
- безопасный код ошибки;
- перечень включённых событий.

### 5.4. Хранение медиа

Предлагаемая структура:

```text
CatDoorData/
├── events/
│   └── YYYY/
│       └── MM/
│           └── <event_uuid>/
│               ├── face.mp4
│               ├── side.mp4
│               ├── thumbnail.jpg
│               └── metadata.json
├── exports/
├── temp/
├── logs/
└── catdoor.sqlite3
```

Правила:

- запись начинается в уникальном подкаталоге `temp`;
- итоговый каталог публикуется атомарным переименованием после проверки;
- перед записью проверяется свободное место;
- путь всегда строится сервером из UUID, а не принимается от браузера;
- абсолютные пути не попадают в ZIP;
- файлы за пределами `CatDoorData` нельзя отдавать через веб-маршрут;
- временные файлы прошлого аварийного запуска обнаруживаются и маркируются, но не
  удаляются без безопасной политики восстановления;
- MP4 по умолчанию добавляется в ZIP без повторного сжатия, чтобы не загружать
  Intel Core i3 бесполезной работой.

`metadata.json` является переносимым снимком метаданных события. Источником истины
до экспорта остаётся SQLite.

### 5.5. Ручное создание события

Пользовательский сценарий:

1. Админка показывает состояние обеих камер и свободное место.
2. Пользователь нажимает «Записать тестовое событие».
3. Web валидирует готовность системы и создаёт `capture_request`.
4. Recorder атомарно забирает запрос.
5. Для обеих камер назначается одна целевая монотонная точка начала.
6. Потоки записываются параллельно во временный каталог.
7. Recorder завершает контейнеры, проверяет читаемость и собирает метаданные.
8. Каталог публикуется, а событие переводится в `ready`.
9. HTMX обновляет статус без полной перезагрузки страницы.

Аппаратной синхронизации в milestone нет. Под «синхронным событием» понимается
единое окно записи, параллельный запуск и сохранение фактических временных меток.
В базе фиксируются:

- плановое начало;
- фактический первый кадр каждого потока;
- продолжительность каждого файла;
- `start_skew_ms`;
- пересечение временных окон.

По умолчанию событие считается полным только при наличии проверенных файлов обеих
камер. При обрыве одной камеры материалы второй сохраняются, а событие получает
статус `partial` и не включается в обычный экспорт без явного выбора.

Одновременная запись двух ручных событий в milestone не поддерживается. Повторная
команда либо ставится в очередь, либо получает понятный ответ «запись уже идёт»;
выбранное поведение должно быть единым для API и интерфейса.

### 5.6. FastAPI, Jinja2 и HTMX

Веб-интерфейс строится как server-rendered приложение:

- FastAPI отвечает за маршруты, валидацию и зависимости;
- Jinja2 формирует полные страницы и повторно используемые фрагменты;
- HTMX обновляет статус камер, запись, журнал, разметку и экспорт;
- собственный JavaScript используется только там, где HTMX недостаточно;
- state-changing запросы выполняются только методами `POST`, `PUT` или `DELETE`,
  а не через `GET`;
- формы защищаются проверкой origin/CSRF в соответствии с выбранной схемой
  локального доступа.

Предварительные пользовательские страницы:

- `/` — сводка: recorder heartbeat, камеры, диск и последняя запись;
- `/settings/cameras` — настройка двух ролей и проверка соединения;
- `/events` — журнал с фильтрами и пагинацией;
- `/events/{event_id}` — карточка события, медиа и разметка;
- `/cats` — минимальный справочник домашних кошек;
- `/exports` — создание, состояние и скачивание экспортов.

FastAPI не должен отдавать произвольный путь из query-параметра. Медиа доступно
только по ID записи из базы после проверки, что вычисленный путь находится внутри
корневого каталога.

### 5.7. Журнал событий

Журнал показывает события от новых к старым и поддерживает:

- серверную пагинацию;
- фильтр по диапазону дат;
- фильтр по статусу записи;
- фильтр `pending / reviewed`;
- фильтр по результату разметки и домашней кошке;
- индикаторы наличия видео с обеих камер;
- длительность и рассогласование;
- превью;
- понятное отображение `partial` и `failed`.

Карточка события показывает оба видео, технические метаданные и историю разметки.
Если браузер не воспроизводит исходный кодек камеры, файл всё равно остаётся
доступен для скачивания, а интерфейс объясняет ограничение. Решение о
транскодировании принимается после проверки реальных камер и не включается
автоматически в milestone.

### 5.8. Ручная разметка

Поддерживаемые результаты:

- `known_cat` — выбрана конкретная активная домашняя кошка;
- `foreign_cat` — чужая кошка;
- `not_visible` — кошку невозможно уверенно увидеть;
- `multiple_cats` — в событии несколько кошек.

Правила валидации:

- `known_cat` обязательно требует `cat_id`;
- остальные результаты не должны содержать `cat_id`;
- размечать по умолчанию можно только `ready` или явно открытое оператором
  `partial` событие;
- повторная разметка не удаляет историю;
- после успешной записи интерфейс показывает сохранённое сервером значение;
- событие без разметки остаётся `pending`.

### 5.9. Экспорт ZIP

Экспорт создаётся из явно выбранных событий или из текущего фильтра журнала.
Обычный экспорт включает только события со статусами `ready` и `reviewed`.

Создание архива выполняется как фоновая задача:

1. Web создаёт запись `exports` и фиксирует перечень `export_items`.
2. Worker переводит задание в `processing`.
3. Для каждого события повторно проверяются пути и наличие файлов.
4. Во временный архив добавляются медиа и переносимые метаданные.
5. Архив проверяется на открытие и наличие обязательного manifest.
6. Вычисляется SHA-256.
7. Временный файл атомарно публикуется в `exports`.
8. Задание получает статус `ready`.

Предлагаемая структура архива:

```text
catdoor-export-<timestamp>-<export_uuid>.zip
├── manifest.json
└── events/
    └── <event_uuid>/
        ├── face.mp4
        ├── side.mp4
        ├── thumbnail.jpg
        └── metadata.json
```

Manifest содержит версию формата, дату экспорта, список событий, разметку,
относительные пути, размеры и контрольные суммы. Он не содержит:

- RTSP URL;
- IP-адреса и учётные данные камер;
- абсолютные локальные пути;
- логи;
- копию SQLite;
- переменные окружения или другие секреты.

Повторный запуск после сбоя должен либо продолжить задание безопасным способом,
либо удалить только собственный незавершённый временный архив и начать его заново.
Готовый архив никогда не перезаписывается.

## 6. Критерии готовности

### 6.1. Настройка камер

- В интерфейсе существуют ровно две обязательные роли: `face` и `side`.
- Для каждой роли можно задать и изменить RTSP-настройки без изменения кода.
- После перезапуска приложения настройки сохраняются.
- Невалидный URL не сохраняется и сопровождается понятной ошибкой.
- Пароль не возвращается браузеру и не появляется в журнале приложения.
- В репозитории и тестовых артефактах нет реальных адресов и секретов.

### 6.2. Проверка соединения

- Для рабочей камеры проверка подтверждает получение декодируемых кадров.
- Для недоступного адреса проверка завершается за настроенный тайм-аут.
- Интерфейс показывает время проверки, состояние, разрешение и кодек.
- После отключения и повторного включения камеры recorder восстанавливает
  соединение без перезапуска всей системы.
- Ошибка одной камеры не меняет корректное состояние второй.
- Устаревший heartbeat recorder явно отличается от состояния `online`.

### 6.3. SQLite и миграции

- Пустая база создаётся штатной миграцией.
- Повторное применение миграций не повреждает данные.
- Foreign keys и ограничения разметки проверяются автоматическими тестами.
- Перезапуск процессов сохраняет журнал, разметку и статусы заданий.
- Одновременное чтение журнала и создание события не приводит к `database is
  locked` в нормальном сценарии.
- В SQLite нет бинарных видео, RTSP-паролей и абсолютных секретных URL.

### 6.4. Ручное событие

- Один запрос создаёт не более одного события.
- При двух исправных камерах создаются читаемые `face.mp4` и `side.mp4`.
- Оба файла соответствуют одному запрошенному временному окну.
- `start_skew_ms` измеряется и сохраняется; на целевой локальной сети рабочая цель
  — не более 500 мс, если реальные камеры и GOP позволяют это обеспечить.
- Фактическая длительность каждого файла отличается от заданной не более чем на
  согласованный допуск, первоначально 1 секунда.
- Частичный или повреждённый файл не помечается как готовый.
- При обрыве камеры событие становится `partial` или `failed`, а recorder
  продолжает обслуживать следующие запросы.
- При недостатке диска запись не запускается, а пользователь получает безопасную
  диагностическую ошибку.
- Остановка Web во время записи не прерывает запись; после запуска Web событие
  видно в журнале.

Целевое значение 500 мс должно быть подтверждено на реальном оборудовании. Если
его невозможно достичь без транскодирования или аппаратной синхронизации, milestone
фиксирует измеренный предел и согласованное новое значение, а не скрывает
рассогласование.

### 6.5. Веб-интерфейс и журнал

- Все основные операции доступны из браузера без командной строки.
- Основные страницы работают без клиентского SPA-фреймворка.
- Список событий имеет серверную пагинацию и заданные фильтры.
- Карточка показывает оба медиафайла или точную причину их отсутствия.
- Ошибки HTMX возвращают понятный фрагмент, а не необработанный traceback.
- Некорректный или подменённый ID не позволяет прочитать файл вне `CatDoorData`.
- Перезапуск Web не влияет на recorder и не теряет сохранённые данные.

### 6.6. Разметка

- Можно создать домашнюю кошку и выбрать её для `known_cat`.
- Можно выбрать `foreign_cat`, `not_visible` или `multiple_cats`.
- Невалидные сочетания типа разметки и `cat_id` отклоняются на сервере.
- Повторная разметка сохраняет историю изменений.
- Фильтры журнала сразу отражают новую текущую разметку.

### 6.7. ZIP-экспорт

- Экспорт содержит только зафиксированный при создании набор событий.
- Архив открывается стандартным ZIP-инструментом на Windows и macOS.
- Manifest соответствует документированной версии схемы.
- Размеры и SHA-256 файлов в manifest проходят повторную проверку.
- В архиве отсутствуют секреты, абсолютные пути, база и логи.
- `partial`, `failed` и `pending` не попадают в обычный экспорт автоматически.
- Большой экспорт не блокирует RTSP-запись и не удерживает транзакцию SQLite на
  время копирования файлов.
- Сбой экспорта не повреждает исходные события и не публикует незавершённый ZIP.

### 6.8. Общая приёмка

- Автоматические тесты проходят на поддерживаемой версии Python.
- Выполнен smoke test на целевой Windows-машине с двумя реальными камерами.
- Проверены разрыв RTSP, перезапуск Web, перезапуск recorder и недостаток
  свободного места.
- Проверено отсутствие сетевых обращений к облачным сервисам.
- Никакой код milestone не отправляет команды контроллеру двери.
- Документация установки, конфигурации, восстановления и формата экспорта
  обновлена вместе с реализацией.

## 7. Стратегия тестирования

### 7.1. Unit-тесты

- валидация и маскирование RTSP-настроек;
- переходы состояний camera worker;
- backoff и ограничение параллельных проверок;
- правила текущей разметки и история reviews;
- безопасное построение путей;
- выбор событий для экспорта;
- генерация и проверка manifest;
- восстановление зависших заданий.

### 7.2. Интеграционные тесты

- миграции на пустой и существующей SQLite-базе;
- конкурентные операции recorder и Web;
- фиктивный RTSP-источник с нормальной работой, тайм-аутом и обрывом;
- полный путь `capture_request → event → media`;
- полный путь `review → export → проверка ZIP`;
- авария между созданием временного файла и публикацией;
- запрет path traversal через маршруты медиа и ZIP.

Тесты репозитория используют только синтетические короткие видео без реальных
кошек, адресов камер и персональных данных.

### 7.3. Проверки на реальном оборудовании

- обе камеры одновременно доступны в изолированном Ethernet-сегменте;
- длительная проверка переподключения;
- серия не менее 20 ручных событий;
- измерение `start_skew_ms`, фактической длительности и нагрузки CPU/диска;
- воспроизведение записей в целевом браузере;
- экспорт и открытие ZIP на MacBook;
- остановка и запуск каждого процесса независимо.

Результаты аппаратной проверки оформляются отдельным отчётом без RTSP URL,
паролей и реальных видеозаписей в Git.

## 8. Порядок разработки

Каждый этап выполняется отдельным небольшим изменением с тестами и обновлением
документации. Переход к следующему этапу происходит после выполнения критериев
предыдущего.

### Этап 0. Зафиксировать контракты

- подтвердить формат локальной конфигурации и способ хранения секретов;
- выбрать media-backend после теста с обеими реальными камерами;
- зафиксировать длительность события и допустимую синхронизацию;
- описать состояния камер, запросов, событий и экспортов;
- согласовать версию формата ZIP manifest.

Результат: архитектурные решения и тестовые RTSP-профили без секретов.

### Этап 1. Основа конфигурации и хранилища

- загрузка конфигурации и переопределение безопасными локальными значениями;
- единый сервис путей внутри `CatDoorData`;
- проверка свободного места;
- миграционный каркас SQLite;
- начальная схема и repository-слой.

Результат: база создаётся миграцией, конфигурация валидируется, пути защищены.

### Этап 2. Проверка RTSP

- абстракция media-backend;
- подключение, получение первого кадра и чтение метаданных;
- независимые состояния двух камер;
- тайм-ауты, backoff, heartbeat и безопасные ошибки;
- fake backend для тестов.

Результат: recorder стабильно показывает состояние камер и восстанавливает связь.

### Этап 3. Каркас Web

- FastAPI application factory;
- базовые шаблоны Jinja2 и HTMX-фрагменты;
- главная страница состояния;
- страницы настройки камер;
- ручная команда проверки соединения;
- единая обработка ошибок.

Результат: обе камеры настраиваются и диагностируются через браузер.

### Этап 4. Очередь и запись события

- `capture_requests`;
- атомарное получение задания recorder;
- параллельная запись двух потоков;
- временные и итоговые каталоги;
- проверка медиа и фиксация `start_skew_ms`;
- восстановление после сбоя.

Результат: при двух исправных камерах создаётся полное ручное событие.

### Этап 5. Журнал и карточка

- пагинированный список и фильтры;
- безопасная раздача медиа;
- карточка с двумя видео и техническими параметрами;
- состояния `ready / partial / failed`;
- превью события.

Результат: все созданные события доступны и диагностируемы из браузера.

### Этап 6. Справочник кошек и разметка

- минимальное управление активными кошками;
- все четыре типа ручной разметки;
- серверные ограничения;
- история исправлений;
- фильтры по текущей разметке.

Результат: оператор может последовательно разобрать очередь `pending`.

### Этап 7. ZIP-экспорт

- фиксация состава задания;
- фоновое формирование;
- manifest, контрольные суммы и атомарная публикация;
- страница статусов и безопасное скачивание;
- восстановление неоконченного задания.

Результат: размеченные события переносятся на MacBook без секретов и ручной
работы с каталогами.

### Этап 8. Отказоустойчивость и Windows

- независимый запуск recorder и Web;
- корректное завершение процессов;
- восстановление после перезапуска;
- длительные RTSP-тесты;
- проверка нагрузки и диска;
- документирование установки и обычной эксплуатации без командной строки.

Результат: milestone проходит общую приёмку на целевом моноблоке.

## 9. Основные риски

| Риск | Последствие | Снижение риска |
|---|---|---|
| Разные RTSP-реализации и кодеки камер | Одна камера не подключается или создаёт повреждённые файлы | Ранний media spike на обеих камерах, изоляция backend, фиксация поддержанного профиля |
| Длинный GOP и разные задержки потоков | Большой `start_skew_ms`, неудобная синхронная разметка | Общая точка старта, фактические метки, измерение пересечения, настройка GOP камеры |
| H.265 не воспроизводится в браузере | Карточка события не показывает видео | Проверить профиль H.264; оставить безопасное скачивание; транскодирование согласовать отдельно |
| Зависшее RTSP-чтение | Recorder перестаёт обслуживать камеру или запрос | Жёсткие тайм-ауты, отдельные workers, контролируемый перезапуск backend |
| Обрыв питания во время записи | Временный или повреждённый MP4 | Временный каталог, проверка контейнера, атомарная публикация, восстановление статуса |
| Конкуренция записей SQLite | Ошибки `database is locked` | WAL, busy timeout, короткие транзакции, отсутствие медиаопераций внутри транзакций |
| Заполнение SSD | Потеря событий или сбой базы | Проверка до записи и экспорта, порог свободного места, предупреждение в админке |
| Утечка RTSP-пароля | Компрометация камеры | Локальный secret config, маскирование, запрет логирования и включения в экспорт |
| ZIP с очень большим набором | Высокая нагрузка и заполнение диска | Фоновое задание, оценка размера, ограничение числа событий, MP4 без повторного сжатия |
| Path traversal или подмена пути в базе | Чтение постороннего файла | Относительные пути, каноническая проверка корня, серверная генерация имён |
| Падение Web во время операции | Незавершённый запрос или экспорт | Персистентные задания, идемпотентные статусы, recorder в отдельном процессе |
| Устаревшее состояние `online` | Пользователь запускает событие при мёртвом recorder | Heartbeat с TTL и отдельное состояние `stale` |
| Ошибочное удаление или повторная разметка | Потеря полезной информации | На milestone нет массового удаления; reviews хранят историю |
| Отличия Windows от среды разработки | Ошибки путей, процессов или поставки FFmpeg | Windows CI где возможно и обязательный smoke test на целевой машине |

## 10. Контрольные точки

Milestone считается управляемым через следующие контрольные точки:

1. **Camera ready** — обе камеры настраиваются, проверяются и переподключаются.
2. **Capture ready** — два файла одного ручного события стабильно сохраняются.
3. **Review ready** — журнал и ручная разметка работают после перезапуска.
4. **Export ready** — ZIP проверяется на Windows и macOS и не содержит секретов.
5. **Operational ready** — recorder и Web независимы и проходят сценарии отказа.

Только после пятой контрольной точки имеет смысл планировать автоматическую
детекцию кошки и инференс следующего milestone.
