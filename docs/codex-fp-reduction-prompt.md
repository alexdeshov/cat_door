## Фаза 1. Motion gating в recorder

Создай новый модуль `src/recorder/motion.py` с классом `MotionGate`.

Алгоритм (чистый numpy, без внешних зависимостей):

- Вход — кадр ветки детектора той камеры (RGB, квадрат входа модели).
- Перевести в оттенки серого взвешенной суммой (0.299R + 0.587G + 0.114B),
  уменьшить до ~80×80 усреднением блоков (не интерполяцией).
- Поддерживать бегущее среднее фона: `B ← (1 − alpha) · B + alpha · F`,
  `alpha` по умолчанию 0.1.
- Маска движения: `|F − B| > delta`, `delta` по умолчанию 12 (шкала 0–255).
- Движение есть, если доля пикселей маски ≥ `min_area_fraction`
  (по умолчанию 0.005, т.е. 0.5% кадра).
- Прогрев: первые 10 кадров после старта или переоткрытия FFmpeg-ветки
  всегда считаются движением (фон ещё не устоялся).

Правила интеграции в src/recorder/app.py — это самая важная часть, читай
внимательно:

- Gating применяется ТОЛЬКО когда автомат событий в состоянии `idle`.
  В состояниях `candidate`, `active`, `tail`, `cooldown` детектор запускается
  на каждом сэмпле безусловно — иначе неподвижно сидящий у дверцы кот перестал
  бы подтверждаться и событие оборвалось бы. Это правило обязано быть покрыто
  тестом.
- Если в `idle` движения нет: детектор НЕ вызывается, `observe()` автомата НЕ
  вызывается, а в detection.jsonl пишется облегчённая запись с
  `skipped_reason="no_motion"`, камерой, `sample_fps` и `frame_age_ms`.
- Фон обновляется только кадрами, обработанными в `idle` (включая
  пропущенные). Вне `idle` кадры в фон не добавляются, чтобы кот не «въехал»
  в фон за время события.
- У каждой камеры свой независимый экземпляр `MotionGate`.

Настройки — по образцу существующих ROI/FPS:

- пер-камерные поля в detection-settings.json: `motion_gating_enabled`
  (по умолчанию false), `motion_delta`, `motion_min_area_fraction`,
  `motion_alpha`;
- стартовые значения из `.env`: `CATDOOR_MOTION_GATING_ENABLED`,
  `CATDOOR_MOTION_DELTA`, `CATDOOR_MOTION_MIN_AREA_FRACTION`,
  `CATDOOR_MOTION_ALPHA`;
- старые JSON без новых полей мигрируются автоматически значениями по
  умолчанию — по тому же механизму, что миграция ROI/FPS (найди её и повтори
  паттерн); тест на миграцию обязателен;
- блок в «Настройках детекции» админки: чекбокс и три числовых поля на камеру,
  с тултипами `?` по образцу существующих (что делает параметр, к чему ведёт
  увеличение/уменьшение);
- изменения подхватываются recorder так же, как остальные настройки детекции
  (при переходе автомата в `idle`).

Наблюдаемость:

- heartbeat дополняется счётчиками за последние 60 секунд по каждой камере:
  `frames_processed`, `frames_skipped_no_motion`;
- админка показывает эти счётчики рядом с состоянием recorder.

Тесты фазы 1 (unit, без реальных камер и весов):

1. Статичная синтетическая сцена: после прогрева `MotionGate` возвращает
   «движения нет».
2. Движущийся блок ~5% площади кадра: «движение есть».
3. Первые кадры прогрева: всегда «движение есть».
4. Автомат не в `idle` → детектор вызывается даже без движения (интеграционный
   тест с заглушкой детектора).
5. `motion_gating_enabled=false` → путь кадра байт-в-байт совпадает с текущим
   поведением: детектор вызывается на каждом сэмпле, новых записей в журнале
   нет.
6. Миграция старого detection-settings.json без motion-полей.

## Фаза 3. Кандидат YOLO26n @416

1. Отдельное окружение экспорта с `ultralytics` (в зависимости проекта не
   добавлять). Модель `yolo26n`, экспорт в ONNX со статическим входом
   `[1, 3, 416, 416]`, end-to-end (NMS-free). Зафиксируй версии ultralytics и
   команду экспорта в отчёте.
2. Скачивание весов — по механизму
   `scripts/prepare_detector_candidate download` с полным SHA-256.
3. Посмотри фактический формат выхода экспортированного ONNX. Если он
   совпадает с контрактом существующего ultralytics-адаптера
   (`xyxy, confidence, class`, NMS уже применён) — переиспользуй адаптер,
   добавив architecture-алиас `yolo26`; иначе напиши отдельный адаптер по
   образцу существующих. В обоих случаях — тест адаптера на синтетическом
   выходе (реальные веса в тестах не используются).
4. Manifest: `architecture`, `license: AGPL-3.0`, `input.shape`,
   `cat_class_id`, `sha256`. Индекс класса cat НЕ бери из памяти — проверь на
   реальном изображении кота, что выбранный индекс действительно даёт высокий
   confidence (у COCO-моделей Ultralytics cat обычно 15, но проверка
   обязательна).
5. Sanity-проверка до замеров: прогони через новый детектор 3 сохранённых
   кадра с размеченным котом и 3 кадра с известными ложными объектами (обувь,
   тень). Кот обязан давать заметно больший confidence, чем ложные объекты.
   Если это не так — не иди дальше: ошибка почти наверняка в preprocessing
   (BGR/RGB, letterbox, scale) — сверь manifest с фактическим экспортом.
6. Замеры — строго по фазам 3–4 из docs/codex-detector-testing-prompt.md:
   bounded latency probe (бюджет медианы 70 мс) и detector-only replay на
   размеченных событиях. Ключевая метрика этой сессии — false trigger rate на
   событиях `not_visible` в сравнении с baseline SSDLite; также miss rate по
   обеим камерам и threshold sweep для стартовых порогов.
7. Активацию модели НЕ выполняй. Подготовь точную инструкцию владельцу: какие
   файлы в `models/`, какое значение `CATDOOR_DETECTOR_MODEL_PATH`, какие
   стартовые пороги по камерам следуют из threshold sweep.
