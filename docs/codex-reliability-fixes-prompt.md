# Промт для исправлений надёжности runtime

Скопируйте текст ниже в новый сеанс Codex на Windows-моноблоке. Основание —
ревью изменений контура метрик и автозапуска от 2026-07-30: найдены три бага,
один из которых может молча останавливать запись до следующего входа в Windows.

~~~text
Ты работаешь с проектом Cat Door AI на целевом Windows-моноблоке. Задача —
устранить три найденных на ревью бага надёжности и добавить watchdog.
Приоритет проекта: recorder не должен умирать молча ни при каких условиях —
лучше деградировать с записью ошибки и повторить попытку, чем остановиться.

Сначала обязательно полностью прочитай:

1. AGENTS.md
2. docs/deployment-windows.md (разделы про автозапуск и журнал autostart)
3. src/recorder/app.py (функции run, monitor_automatic, _register_loaded_models)
4. src/common/database.py
5. src/common/online_metrics.py
6. src/web/app.py (endpoint /api/evaluations)
7. training/evaluation_job.py

Ограничения: всё локально; секреты и RTSP URL не попадают в журналы и Git;
реальная дверь не управляется; ветка `fix/runtime-reliability` от актуального
`main`; после каждой фазы — ruff, mypy, полный pytest.

## Фаза 1 (критичная). Recorder не должен умирать

Проблема: цикл перезапуска `run()` в `src/recorder/app.py` ловит только
`DetectorError, RuntimeError, ValueError`. При этом `monitor_automatic`
пробрасывает `OSError` и `SQLAlchemyError`, а `sqlite3.OperationalError` из
`apply_migrations` не ловится нигде. Новая регистрация моделей в SQLite при
старте (`_register_loaded_models`) создаёт гонку с web-процессом ровно в момент
автозапуска при входе в Windows: оба процесса одновременно прогоняют миграции и
пишут в одну базу. Итог возможен такой: recorder падает молча, и до следующего
входа в систему запись не работает.

Исправления:

- в `run()` перехватывать `Exception` (не `BaseException`): записать тип ошибки
  в recorder-status и в detection-журнал, подождать и повторить попытку;
  сохранить текущее поведение для `KeyboardInterrupt`/`SystemExit`;
- добавить ограниченные ретраи с паузой вокруг стартовых операций с базой
  (миграции, регистрация моделей) — конфликт блокировки при одновременном
  старте двух процессов должен переживаться, а не убивать процесс;
- включить для SQLite режим WAL и `synchronous=NORMAL` в
  `create_session_factory` (`src/common/database.py`) — база используется
  двумя процессами одновременно; busy timeout оставить;
- тесты: имитация `SQLAlchemyError`/`OSError` из monitor-цикла не завершает
  `run()`; повторная попытка фиксируется в статусе.

## Фаза 2. Rolling-метрики: события без предсказаний — это не отказы

Проблема: в `src/common/online_metrics.py` размеченные события, не имеющие
предсказаний активной версии модели, получают `no_prediction`, который
`calculate_metrics` засчитывает как false reject. После установки новой
identity-модели все ранее размеченные события мгновенно записываются ей в
отказы: FRR раздувается, окно «за всё время» теряет смысл.

Исправления:

- события без предсказаний активной версии исключить из расчёта FAR/FRR/
  uncertain и показывать отдельным полем «покрытие»: сколько размеченных
  событий имеют предсказание активной версии, сколько — нет;
- `no_prediction` от активной версии (модель запускалась, но кадров с котом не
  было) продолжает учитываться как сейчас — исключаются только события вообще
  без записей этой версии;
- обновить страницу метрик и `docs/metrics.md`; тесты на смену версии модели:
  старые события не превращаются в отказы новой версии.

## Фаза 3. Зависшие оценки не должны блокировать новые

Проблема: `/api/evaluations` отвечает 409, пока существует run в статусе
`starting`/`running`. Job персистит `failed` при исключениях, но при жёстком
завершении процесса (питание, OOM, диспетчер задач) статус остаётся `running`
навсегда — новые оценки блокируются насовсем.

Исправления:

- job периодически обновляет heartbeat (метку времени) в своём `status.json`
  и/или строке run — обновление уже происходит по ходу обработки, достаточно
  гарантировать периодичность;
- web при проверке активного run считает его зависшим, если heartbeat старше
  разумного порога (например, 10 минут), переводит в `failed` с пометкой
  «прерван без завершения» и разрешает новый запуск;
- та же защита — для локального обучения (`/api/training/local/start` читает
  `status.json` со статусами `starting/preparing/training`);
- тесты: устаревший running-run автоматически помечается failed и не блокирует
  новый запуск.

## Фаза 4. Watchdog

Автозапуск через реестр `Run` запускает компоненты один раз при входе. Если
recorder упал, ничего его не перезапустит. Добавить супервизию без прав
администратора:

- отдельный лёгкий скрипт `scripts/watchdog.py`: проверяет свежесть
  `recorder-status.json` (порог staleness) и ответ web на `127.0.0.1`; мёртвый
  или зависший компонент перезапускает через существующие
  `scripts/start_recorder.py` / `scripts/start_web.py`; каждое действие пишет в
  `runtime/watchdog.jsonl` (без секретов);
- защита от щёлканья: не перезапускать один компонент чаще, чем раз в N минут;
  после M неудачных перезапусков подряд — записать ошибку и ждать;
- запуск: задача планировщика Windows текущего пользователя (schtasks без
  прав администратора) каждые 5 минут, установка/удаление/статус — расширить
  `scripts/manage_autostart.py`;
- watchdog не должен убивать живой процесс: только запуск при отсутствии
  признаков жизни; двойной запуск компонента недопустим — проверять, что
  существующий процесс действительно не отвечает (staleness heartbeat), а не
  просто перезапускать всегда;
- обновить docs/deployment-windows.md; тесты логики принятия решения о
  перезапуске (файловая система и время — через подменяемые зависимости).

## Проверка на реальной машине

После фаз: перезапустить web и recorder штатно; убедиться, что heartbeat
свежий, `autostart.jsonl` содержит пары starting/started, watchdog установлен
в планировщике и его журнал пуст (нет ложных перезапусков). Затем аккуратно
завершить процесс recorder через диспетчер задач и убедиться, что watchdog
поднял его в течение цикла и записал это в журнал. Итоги — в
`docs/session-history.md`.
~~~
